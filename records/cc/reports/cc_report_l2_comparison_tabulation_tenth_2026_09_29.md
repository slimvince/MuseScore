## 7. Findings of the run

1. **A parallel guard runner — measured, put as a candidate, not built.** The user asked during the session whether
   the guard set's 80 tools could run in parallel threads, and said to record such a candidate in the report if a
   measurement shows it would be substantially quicker. The closing capture took 7 min 55 s of wall time. The timing
   of each guard, run one at a time exactly as the runner invokes it by a scratch script that imports the runner's
   authored list and writes nothing in the repository, is at Appendix D (`guardtime.txt`).
   **What it measured:**

   - **The time is not spread evenly.** The 80 guards took 472.8 s run one after another, matching the capture's
     7 min 55 s. Six guards take about three quarters of it: `gen_test_construction_evidence.py --check` alone takes
     155.0 s (a third), then `gen_doc_change_candidates.py` 52.8 s, `gen_cluster_dispositions.py --producible` 48.1 s,
     `gen_retirement_caller_check.py` 35.9 s, `gen_cluster_dispositions.py --verify` 33.3 s and `reaim_home_anchors.py`
     33.1 s. 64 of the 80 take under 5 s, 58 of them under 1 s.
   - **What follows by arithmetic.** A parallel run can never finish before its slowest guard, so about 155 s is the
     floor. Laying the measured times out over four workers, slowest first, the other guards (317.8 s together) fit
     beside that one in about 106 s per worker. So four workers would bring the run to about 155 s, roughly 2.6 minutes
     against 7.9 — **about three times quicker**. More workers would not help, because the one 155 s guard sets the
     floor.

   This is arithmetic on sequential timings: it assumes the guards do not slow each other down when they run together,
   and that assumption is not measured. **On the user's stated condition — a substantial gain — this is recorded as a
   candidate.** A second, separate observation: the guard that sets the floor is one of the twelve standing reds, so a
   change to it, not a parallel runner, is what could lower the floor further.
   **Nothing is built and nothing is decided here.** `gen_guard_state.py` is outside this dispatch's write set (A4).
   Before a parallel runner could be relied on, three things would need checking: that no guard writes a file
   another reads; that none takes a git lock; and that a parallel capture matches a sequential one verdict for verdict.
2. **`git hash-object` on working-tree and scratch files prints a line-ending warning.** Git warns that a line feed
