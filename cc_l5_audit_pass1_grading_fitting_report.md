## 5. Findings (each maps to an OPEN_ITEMS row in the fold commit)

**Fit-manifest integrity — `param_manifest.json` is validated by nothing and read by
nothing.** No `.py` or `src/composing` file imports/reads `tools/param_manifest.json`
(grep clean). It is a hand-maintained snapshot of the fit surface with no consumer and no
cross-check against the C++ source. Fact-publication corollary: a published fact consumed
by no one is dormant or waste. *(first-rank; establishment/integrity)*

**Fit surface is triple-represented.** The C++ source (truth), `param_manifest.json`, and
`stage5_fit_driver.PARAMS` (49 rows, lines 67–146) each carry the same parameter values
(one concern, three paths — #6). The ONLY cross-check is the driver's `fixture`
aggregate-root reproduce test, which detects a wrong PARAMS value **only for params that
materially move root-%**; the many zero-sensitivity params (per `param_manifest.json`)
can drift undetected. *(first-rank; #6 duplication + establishment gap)*

**Two key-parsing conventions for one concern.** `compare_rn._our_key_tonic` /
`_dcml_key_tonic` (the robust-unit key-agree path) vs
`oracle_root_metric.parse_our_key` / `parse_dcml_key` / `parse_m21_key`
(oracle_root_metric's KEY tiers) are two independent implementations of "key string →
(tonic, mode)". A divergence would make the two instruments disagree on key correctness.
oracle_root_metric's docstring notes its parsers are "ported verbatim from the ratified
decomposition diagnostic" — i.e. a fork of a diagnostic, not the compare_rn path. *(#6)*

**Grading/fitting chain skips the anti-contamination manifest guard.** `calibration_fit`
and `c1_reliability` read both the corpus (`tools/corpus/{preset}`) and the km/fs substrate
WITHOUT `validate_corpus_dir` — the guard the metric tools (`characterise_bir_false`,
`oracle_root_metric`, `analyze_inversion_errors`) enforce. A stale or preset-contaminated
corpus/substrate passes silently into the reliability curves and the calibration maps.
*(establishment asymmetry + silent-failure)*

**oracle_root_metric docstring figures are stale.** Docstring (lines 61–62) states
per-record charged 3882/4083/3914 and deduped 3862/4065/3894; at HEAD the tool produces
3878/4084/3910 and 3858/4066/3890 — the −4/+1/−4 pattern of the L3-wiring delta. Hand-
transcribed measurement figures in a docstring, drifted. *(#10 / #17f)*

**stage5_fit_driver docstring names the superseded/stale regression stop.** Lines 12–13
describe the per-evaluation constraint as "no NEW class-(b) batch-stop case (vs the
CLAUDE.md 53/24/53 identity sets)". The **code** computes the constraint from the a8
robust-unit mapping (correct per CLAUDE.md block A, which SUPERSEDED the batch stop), and
the live gate is **52/24/52** (the fixture prints batch=52/24/52). The prose lags the code
on both the unit and the integer. *(#10 doc-drift within the instrument)*

**Broad except-swallows silently reduce the measurement denominator (15 sites).** Across
`analyze_inversion_errors:149` (WiR parse), `oracle_root_metric:159,169`,
`c1_reliability:169,187,196,237,246,292`, `calibration_fit:57,77,86,122,131` a broad
`except` drops a score/region/value with no stderr signal. Most consequential:
`music21_batch:199` — a `chordify()` failure yields a **0-region `.music21.json` silently
written into the corpus**, removing that score from the oracle denominator with no signal.
*(silent partial-coverage path)*

**Dangerous default output paths overwrite committed references.** `music21_batch`
default `--output tools/corpus` overwrites the canonical committed corpus;
`calibration_fit` default `--out-dir tools/calibration_maps` overwrites the committed maps;
`stage5_fit_driver split` overwrites the committed `stage5_split_registry.json`. (The
`fit`/`audit` appends to `tools/fit_ledgers` are by design, O-8 — not flagged.) Combined
with the unenforced music21 version pin, a default-arg music21_batch run silently
re-baselines committed ground truth. *(dangerous default; ties to the version-pin finding)*

**analyze_inversion_errors: value-copied constant + dangling anchor + wrong error path.**
`INVERSION_SUSPICION_MARGIN = 0.70` (line 322) copies the production pref
`inversionSuspicionMargin` (silently stale if the pref moves). The comment above (line 321)
cites "chordanalyzer.cpp ~1916-1923 (seventh-exemption guard)" but the file is only **1610
lines** — a dangling anchor. The empty-input error (line 104) prints "No .ours.json files
in tools/reports/corpus/" but the code reads `corpus_dir` (default `tools/corpus/baroque`)
— stale/wrong message path. *(value-copied constant + dangling anchor + misleading message)*

**Grading tolerances/buckets with no cited provenance (13 UNFIT literals).**
beat window ±0.26 (analyze_inversion_errors:273–276); noteCount≥3 "genuine chord"
(260,289,292); margin≥2.0 "likely correct, fix won't help" interpretation (215);
near_logistic 0.05 (calibration_fit:219); min-cell 50/20 (199); FloatingKey ±4 flats/sharps
(music21_batch:193–194). Each is a measurement decision with a hand-set value and no
recorded rationale. *(UNFIT constants)*

**Dead computation.** `analyze_inversion_errors:214` computes `lt_2 = count(margins<2.0)`
which is never printed or used. *(minor; dead code)*

**Establishment notes (not defects, recorded).** The stage5 `RATIFIED` fixture targets
