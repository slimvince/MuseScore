# OI-254 — Non-conformance: the status-bar harmonic annotation is unlocalized and outside the accessibility tree, against the ratified §12.1 localization and accessibility statements

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — notation / presentation / decision-conformance (the [[OI-231]] pattern: decision
cited, departing code cited, no fix here).**

## The decision

`ARCHITECTURE.md:5854-5858` (§12.1), verbatim in part: "All user-visible strings use MuseScore's
existing Qt localization infrastructure (`.ts` files, Qt Linguist). English and Swedish
translations provided for all new strings. Accessibility follows MuseScore's existing Qt
accessibility patterns…" — register entries D-118/D-119 (the §12.1 rules). The user re-stated the
localization requirement directly on 2026-08-01 (anything user-visible and language-dependent
uses MuseScore's multilanguage architecture).

## The implementation

- The harmonic annotation strings are built by raw string concatenation with no translation call
  (`notationcomposingbridge.cpp:835-844` — no `qtrc`/`TranslatableString` anywhere on the path);
- the annotation reaches the user by plain-text append to the accessibility info
  (`notationaccessibility.cpp:203-207`), and is never added to `screenReaderInfo` /
  the engraving accessibility surface — `harmonicAnnotation` has exactly one caller.

So the one user-visible harmonic string on the default interactive path is untranslatable and
invisible to the accessibility patterns §12.1 names. English-only today also means the
English-and-Swedish provision for new strings is unmet.

## Disposition

A presentation-layer completion at its #8-correct stage (wrap the user-visible strings in the
localization infrastructure; route the annotation through the accessibility surface §12.1 names),
with the string-catalog side (`.ts` entries, English + Swedish) part of the same act. Not an
inference change anywhere. Not fixed here.
