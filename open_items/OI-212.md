# OI-212 — The record producer analyzes the whole score regardless of the requested span

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — the analysis-cost / notation-surface cluster (cost multiplier + analysis-input scope change)**

**The fact.** `produceNotationRecord(score, stem, excludeStaves)` takes **NO tick range**
(jointnotationproducer.h / .cpp). All four record-arm seams call it and analyze the **ENTIRE score**,
narrowing the result by view AFTERWARD:
- the span-annotation emitter — `notationcomposingbridge.cpp:1495`;
- the implode chord-track — `notationimplodebridge.cpp:1420`;
- the region tuning path — `notationtuningbridge.cpp:777`;
- the note-seam funnel `analyzeHarmonicContextAtTick` — `notationcomposingbridge.cpp:732`.
The span view (`spanViewSegments`) and note view (`noteView`) are pure lookups applied to the
whole-score record, not a bound on what is decoded.

**What the legacy arm did instead.** Every legacy arm passed the **actual span** into
`analyzeHarmonicRhythm` (`notationcomposingbridge.cpp:1509`, `notationimplodebridge.cpp:1434`) — for
Roman numerals, the selection plus a deliberate ≈8-bar lookahead (`kMaxPivotLookaheadRegions`). So the
record arm both (a) **multiplies cost** — a whole-score decode where the legacy arm decoded a bounded
window — and (b) **silently changes the analysis INPUT SCOPE** — the answer for a span is now a function
of the whole score, not of the span plus its bounded lookahead.

**Why this is a row, not just a performance note.** The scope change was made by dispatch specification,
not by a ruling, and it contradicts the notation output-surface contract's own span seam ("the caller
names a score span; the record for that span is returned"). It is the concrete mechanism behind the
extent question [[OI-210]] and the interactive-latency regression [[OI-206]] / [[OI-203]]. The cost side
is quantified by the analysis-cost dispatch's phase profile and scaling law; the scope-change side is a
decision-conformance item ([[OI-207]]) — a whole-score analysis input adopted where a bounded one was
the prior ruling. The layer-correct resolution (if the extent ruling calls for it) is a **span input at
the producer/adapter** — an input-scoping parameter, NOT an inference change (the [[OI-204]] pattern for
the staff axis, here for the temporal axis).

**Envelope caveat carried.** On the chorale-scale established envelope the whole-piece reading and a
bounded ≈4–8-measure reading are measured equal in both committed output and ground-truth accuracy
(the OI-206 Task 2 window study); the scope change costs no correctness THERE. Whether it does beyond
the envelope (the 3.1b / Tristan concern) is unmeasured and is a fix-surface input.

**Dated note — 2026-08-01 (CC, the [[OI-207]] adjudication): the ratified decision this contradicts
is now named, and it is not the one this row cites.** This row cites "the contract's span seam
specifies the opposite". The adjudication read the layer specifications in full and found a
**stronger and older** decision, ratified by the user on 2026-07-02 and recorded in the canonical
architecture document: the **Bounded-context contract**, `ARCHITECTURE.md:798-802`, register entry
**D-030**. Verbatim, the binding requirements:

> The binding scale requirements: **(R1)** cost scales with the working span, not the whole
>   score; **(R2)** re-analysis is incremental over the dirty span plus a bounded margin; **(R3)**
>   the working span is **extensible**

and, register entry **D-031**, `ARCHITECTURE.md:802`:

> Whole-score analysis is the degenerate case (selection = score).

`ARCHITECTURE.md:802-806` records it as "the ONE detailed cross-layer spec for this contract"
(`cowork_bounded_context_design.md`) and, per the 2026-07-02 user directive, as **"the hard gate
before L6"**. The behaviour this row records is specified in the same document at
`ARCHITECTURE.md:114` (register entry **D-011**): "WHOLE-score decode ONCE; deterministic; NO
caching". So the canonical architecture document specifies both, and R1 is contradicted on every
seam. Nothing here changes this row's status or disposition — it names the decision, per the
[[OI-208]] ruling that a non-conformance row points back at what it violates.
