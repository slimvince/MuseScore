# OI-339 — A guard failed once and passed on every later run with no intervening write; the cause is not established and the record does not name the guard

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — instrument / measurement layer (the audit's own guard apparatus). Rowed 2026-08-04
(CC, `cc_instruction_finish_line_item1.md`, Task 2) on the user's ruling R2.**

## The finding, as the record carries it

At the census-delegation wave (2026-08-04) a guard in the derived guard list **failed once and then
passed on every later run of the same session, with no intervening write to anything it reads**. The
session additionally established that the guard's `--check` path depends only on **two files that
nothing in the guard list writes**, which is what makes the transition unexplained: the inputs could
not have changed between the failing run and the passing ones by any act inside the wave.

**The cause was not established, and no fix was attempted** — the wave was under a freeze on
repairing guards, and a repair without a cause would have been a guess.

The record of this is `STATUS.md`'s census-delegation entry, in its own words: *"a guard failed once
and passed on every later run with no intervening write, and its `--check` path depends only on two
files nothing in the guard list writes — cause NOT established, and no fix attempted under the
freeze."*

## What this row cannot supply, and why it says so rather than filling it in

**The record does not name the guard.** The observation is carried only in the `STATUS.md` sentence
above, which describes it without identifying it; the session's own artifacts do not record it
either — `tools/audit/guard_state.json` holds each guard's FINAL verdict for the run that produced
it, so a guard that failed transiently and then passed leaves no trace in it. A repository-wide
search for the observation's own phrasing returns that one sentence and nothing else.

So the first act of whoever works this row is **to identify the guard**, and that identification is
not attempted here: the never-work-from-memory rule and the no-guessing rule both forbid supplying a
name the record does not hold, and a wrongly-named guard in a row is worse than an unnamed one —
it sends the next session to the wrong tool and reads as established.

**One partially-matching candidate, recorded at low confidence rather than dropped (#12) and
explicitly NOT an identification.** `tools/audit/guard_armed_check.py` checks that the shell-read
guard is declared as a `PreToolUse` hook, and its inputs are settings files that nothing in the
guard list writes — which matches the "files nothing in the guard list writes" half. **It does not
match the count:** its own output records reading **three** settings files
(`.claude/settings.json`, `.claude/settings.local.json`, and the user-level
`C:\Users\vince\.claude\settings.json`), where the record says two. It is written down because a
ruled-out-or-uncertain possibility is information, and it is flagged this plainly so no later reader
mistakes it for the answer.

## Why it is worth keeping at all, given that it currently passes

A guard whose verdict moves without its inputs moving is a guard whose PASS carries less than a
reader takes it to carry — the same shape [[OI-333]] records for a different cause (a `--check` that
re-reads instead of re-deriving, and therefore cannot fail on the thing it appears to watch). The
difference is that OI-333's defect is understood and this one is not, which is precisely why it is
recorded rather than left to be re-noticed.

## What is NOT in doubt

No analysis behaviour, no measurement of the analysis, no register entry and no open-items status.
The guard concerned is part of the audit's own apparatus for watching its artifacts, and at every
run since the one failure it has passed.

reconciled.** D-641 decides what a finding is OWED; D-438's declaration decides what a STAGE WAITS

overrides the other.** Under D-438 this row **GATES by the declaration's own default**: its subject

what it does when a new row IS a candidate. The same is true of every other guard row — [[OI-328]],

**No gating verdict is hand-added here.** The non-gating set is derived and never hand-listed;

for a row the cut never reached is exactly the hand-listing `CLAUDE.md` forbids"*). Whether this
row's D-438 verdict should move is the user's, exactly as [[OI-336]] is.

**The #19 question was asked rather than assumed.** D-641's stated exception is that an
establishment obligation always gates whatever its subject, and "a guard whose passing may not mean

the ruling's and not this row's inference from it. It is recorded here so that a later session
reading only the verdict can see that the question was put.
