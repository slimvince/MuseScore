# OI-379 — Ruling 4's forward bound has a mechanism and the mechanism has no trigger

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Rowed 2026-09-07 (CC, `cc_instruction_status_forward_bound_second_2026_09_07.md` Task 2).** The
identity was MEASURED across both the INDEX and `open_items/` before it was written, not asserted: a
search of the whole tree found no row `OI-379` and no row identity numbered 379 or above anywhere,
`OI-378` being the highest and present exactly once, in section D; and a directory search of
`open_items/` found no `OI-379.md`.

**What this row is about.** Ruling 4 of `cowork_rulings_2026_08_17_governing_surface_split.md` gave
`STATUS.md` a permanent bound and a forward clause to maintain it. `tools/audit/gen_status_batch_bound.py`
is the mechanism that clause installs, and **the mechanism works**: it reads each entry from a git
object at an authored base commit, matches it verbatim in the live file, refuses to proceed unless
each occurs exactly once there and is absent from the archive, and moves it whole. Nothing is ever
retyped. **What is missing is not the mechanism but the trigger.**

## The finding, every clause of it read at the tool's own source

- **Six values are AUTHORED and re-aimed by hand at every batch close:** `BASE_COMMIT`,
  `PREVIOUS_BATCH_DISPATCH`, `ACT_DATE`, `DISPATCH`, `TASK` and `MOVE_KIND`, together with one row
  appended to `PREVIOUS_AIMINGS`. *(`MOVE_KIND` is the sixth and was added to the tool on 2026-09-07,
  in the same batch that opened this row, under the user's ruling of that date. The five that
  preceded it are the five the withdrawn dispatch's successor named.)*
- **`--check` reconciles only the aiming currently authored.** It re-derives `build()` and compares
  it against the committed artifact. Both sides read the same authored fields, so the comparison
  cannot see a move that was never aimed at.
- **Therefore a close that never re-aims the tool leaves the guard GREEN and the bound UNMET.**
  Nothing in the guard set distinguishes *the last aimed move is intact* from *the bound is met*.

## What happened, and what it cost

Six consecutive batch closes omitted their own move, in this order:

1. `cc_instruction_l2_keyword_count_2026_09_04.md`
2. `cc_instruction_l2_criterion_write_2026_09_04.md`

Each is named by its dispatch and never by a line number (**D-307**). Seven entries stood in
`STATUS.md` that Ruling 4 says should not, and through all six closes the tool's own guard reported
PASS — which is the finding, not a side effect of it.

**The backlog was cleared late**, by `cc_instruction_status_forward_bound_second_2026_09_07.md`
Task 1: six re-aimings of this same tool, oldest omission first, every move byte-faithful and every
reconciliation green in both limbs. **It was cleared BY THE MECHANISM and not by hand** — the route
the withdrawn dispatch `cc_instruction_status_forward_bound_2026_09_07.md` ordered instead, on a
premise the executing side established false at the object and STOPped on
(`cc_report_status_forward_bound_2026_09_07.md`).
