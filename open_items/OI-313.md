# OI-313 — `hardening_battery.py` gate 5 regenerates on the legacy arm and byte-compares against the joint corpus, so it cannot pass

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — instrument / measurement layer. Rowed 2026-08-03 (CC, phase 1y), found while
tracing the `--joint-inference` omission to every regeneration site in the tree (Task 2.1).**

## The mechanism, read at the object

`tools/audit/hardening_battery.py:167-183`, gate 5 (`gate_corpus_regen`, opt-in behind
`--corpus-regen`, described in the module docstring as the expensive check run on a
`batch_analyze.cpp` touch):

1. `:173-174` runs `run_bach_preset.py --preset <P> --corpus-dir tools/corpus --output-dir
   <scratch>/regen/<p>` — **with no `--joint-inference`**, so the regen produces LEGACY
   `analyzeScore` output (`tools/batch_analyze.cpp:4917`, `:5590` — the flag is opt-in);
2. `:176-179` compares each produced file's sha256 against `tools/corpus/<preset>/<stem>.ours.json`;
3. `:182` passes iff `total_bad == 0`.

The comparison target is the JOINT arm — established at the object for all three gate corpora,
352/352 files each carrying `"analysisPath": "joint"`, recorded at
`tools/audit/corpus_arm_backstamp.json`. The two pipelines produce different output **by design**:
that difference is the whole content of the OI-178 adoption.

## Why this is a finding and not a nit

The gate's pass condition is unreachable, and its failure does not say so. A session running it
would see every score differing and read that as "`batch_analyze.cpp` has regressed" — the exact
misreading the gate exists to prevent, produced by the gate itself.

## What it is NOT

**Not the OI-307 defect.** Gate 5 writes into a scratch directory, so it destroys nothing; what is
broken is the comparison, not the corpus. And **not a fault of the other four gates** — calib,
validate, fixture and the register gates do not regenerate.

## Why it went unnoticed

It is opt-in and expensive, so nothing has run it since the OI-178 adoption of 2026-07-26 made the
destination corpus joint-arm output. The same shape as OI-305: a check nobody ran does not report
that it has stopped meaning anything.

## The fix is a judgment, which is why it is rowed

Two different questions about `batch_analyze.cpp` are available and the gate must choose one:

- **pass the flag** — compare joint against joint, which pins the production path; or
- **keep the legacy regen** and compare against a legacy-arm reference, which pins the dormant
  path the OI-180 retirement map deletes.

Either way the fix owes a measured detection under **D-436** as amended: the gate must still catch
a real `batch_analyze.cpp` change, which is the property it was built for.
