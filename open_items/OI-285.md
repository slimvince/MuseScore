# OI-285 — The eight ratification-surface documents are UNCOMMITTED, and the register now cites two of them as the provenance of ratified decisions

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section F — doc-sync debt (#10) / #12, no information loss. CC-found 2026-08-03 at phase 1k, on

## The finding

Every one of the documents that carried a ratification queue to the user exists **only in the
working tree**. Verified at the objects this session, against commit `b6be14097e`:

| document | state at `b6be14097e` |
|---|---|
| `cowork_pending_ratifications_next_session.md` | **absent** — `git cat-file` reports "exists on disk, but not in" the commit |
| `cowork_decisions_pending_ratification_2.md` … `_8.md` (seven files) | **untracked** |

These are not scratch notes. They are the surfaces on which the user was asked to rule, and the
project's own rule makes the surface part of the ruling: a decision is only readable against the
text it answered (`CLAUDE.md`, *the whole decision surface is delivered as user-visible text before
any choice question*, D-249). Nine register entries — **D-406…D-414** — now record their
ratification as "the phase-1j queue presented at `cowork_pending_ratifications_next_session.md` §2",
and that file in turn names `cowork_decisions_pending_ratification_8.md` as where the nine complete
entries were read. Uncommitted, the citation chain resolves to nothing a future reader can open.

The exposure is ordinary and total: an uncommitted file is one `git clean`, one machine change or
one working-tree reset away from gone, and there is no snapshot of it anywhere else.

## What was done at phase 1k, and what was left

**One file was committed:** `cowork_pending_ratifications_next_session.md`, because the phase-1k
dispatch directed that its status block be flipped to RULED and that it not be deleted (#12), and
because nine register entries were given it as their provenance in the same wave. Editing a document
into the record and then leaving it outside the record would have been the worse of the two
inconsistencies.

**Seven were not.** `cowork_decisions_pending_ratification_2.md` … `_8.md` are another session's
working files; adding them was outside anything this dispatch licenses, and the judgment about
whether a per-event reading aid belongs in the repository at all is not a session's to make
unilaterally. They are named here so the decision is a decision rather than an omission.

## What is NOT in doubt

The ratifications themselves. The user's rulings of 2026-08-02 and 2026-08-03 are recorded per entry
in `backbone_decisions.json` and rendered into the register, which is committed; this row is about
the SURFACE the user read, not about whether the ruling happened.

## Disposition

A choice for the user or for Cowork, not a doc-sync act, because it decides what class of document
the repository keeps:

- **(a) Commit all seven** — they become the durable record of what was put to the user at each of
  the eight ratification events, matching how every other decision surface in this project is kept.
- **(b) Commit none and stop citing them** — the register's provenance would then name the ruling
  and its date without naming a file it cannot resolve, which is honest but loses the wording the
  user actually read.
- **(c) Fold each into the register entries it served** and delete the files, which is the #6 answer
  (one home) but is a substantial rewrite of provenance fields already ratified.

Cowork owns these files and should rule; nothing here should be done by a session on its own
judgment.
