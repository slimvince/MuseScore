# OI-242 — §12.1a's recorded reason is false at HEAD: the note-seam analysis costs seconds, not "well under 1ms"

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section F — docs / #10 (DT-12). Found by the [[OI-207]] register completion pass, 2026-08-01, on
the first full reading of `ARCHITECTURE.md` §12.**

## The two sides

`ARCHITECTURE.md:5823-5827`, the recorded reason for the harmonic-display preference, verbatim:

> A user preference controls whether harmonic analysis is shown in the status bar. This
> preference exists for UI clarity — some users find the chord and key information
> distracting, particularly when doing work unrelated to harmony. It is not a performance
> control: analysis cost is negligible (well under 1ms) and suppressing the display does
> not require skipping the analysis.

Both clauses are false on the production path since the notation switch (2026-07-27):

**"analysis cost is negligible (well under 1ms)"** — the note-seam funnel runs
`produceNotationRecord`, a whole-score decode, synchronously per single-note selection.
[[OI-206]] records the mechanism confirmed at the code and the field pattern fully reproduced;
[[OI-203]] records the latency measured (`tools/joint_estimator/noteseam_latency.json`), and the
analysis-cost profile puts the decode in the seconds-to-tens-of-seconds range on the committed
large scores. The "well under 1ms" number described the LEGACY bounded-window path with its decode
cache, which the record arm bypasses by construction.

**"suppressing the display does not require skipping the analysis"** — [[OI-206]] Task 1 established
that the note-seam status bar is the **sole per-selection payer**: the other consumers (implode,
tuning, annotate, the context menu) are action-scoped, not selection-scoped. So on the production
arm, suppressing the display is precisely what would skip the per-selection analysis.

## What this is, and what it is not

It is a **documentation defect, not a design decision to revisit**. The preference's *purpose*
(clarity, not cost) may well still be the right one; what is false is the stated basis for calling
it "not a performance control", and a reader meeting §12.1a today is told the opposite of what the
production path does.

It is also **not a duplicate of [[OI-203]]/[[OI-206]]**, which track the latency itself and its fix.
This row tracks the one sentence in the canonical architecture document that a future design would
read as licence to ignore the cost.

`DECISIONS.md` D-157 records the decision with the contradiction stated in its **Why** field rather
than silently carried.

## Disposition

One paragraph correction in `ARCHITECTURE.md` §12.1a, sequenced with the other architecture-document
corrections ([[OI-232]] / [[OI-233]] / [[OI-236]] / [[OI-238]] / [[OI-107]] / [[OI-112]]) so one
pass touches the document once. What the corrected text says about whether the preference *becomes*
a performance control depends on the [[OI-203]]/[[OI-206]] fix and should not be written ahead of it.

*Resolution belongs in the INDEX row; dated notes may be appended here.*
