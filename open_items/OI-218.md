# OI-218 — Correction of record: incremental patching of the joint decode is UNMEASURED, not refuted

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — the analysis-cost / notation-surface cluster (a correction of a recorded conclusion; sealed §S finding S4)**

**The correction (Cowork, §S).** CC's analysis-cost report concluded that "the coupled DP dominates and
is not reusable across windows, so incremental patching saves ≤ 40 %." **That does not follow.** The
40.5 / 59.5 content-vs-DP split is the cost share of a *cold whole-piece decode*; it does NOT establish
that an edit forces full recomputation. Whether the semi-Markov recursion admits a bounded LOCAL
re-solve on an edit (re-decoding only the affected boundary neighbourhood, reusing the unaffected DP
prefix/suffix) is **unmeasured**. Incremental patching must be recorded as **UNMEASURED, not refuted**.

**The second, unstated caveat.** The 40.5 / 59.5 split is **Python-derived** (the byte-identical Python
reference envelope). A cost *fraction* does not transfer automatically to the C++ decode, whose cost
structure differs (see [[OI-216]] — the C++ decode's `std::string`-keyed state is a cost component the
Python reference does not have in the same form). So even the "≤ 40 %" figure is not established for the
production C++ path.

**Consequence.** The incremental-patching / once-then-patched frequency axis of the analysis-extent
question ([[OI-210]]) remains genuinely OPEN — it was not closed by the analysis-cost profile. A future
measurement should re-solve a bounded neighbourhood after a synthetic edit and compare against the cold
decode, on the C++ path. **Record only** (a correction to the record; no build). Related: [[OI-210]]
(the extent/frequency decision this feeds), [[OI-212]] (the producer's no-span-input, the input-scoping
counterpart), [[OI-203]]/[[OI-213]] (the record-cache increments patching would inform).
