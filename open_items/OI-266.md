# OI-266 — The session handoff's working-protocol standing rules have no specification home

**Section F — doc-sync debt (#10) / documentation gap. Found by the [[OI-207]] residual second

enumerated; these six were never in the register at all, so the homing pass could not reach them.**

## The finding

`cowork_handoff.md` carries a block of standing rules for how the work itself is run. Six of them
are decisions in the register's sense — a stated rule, most with a named ratifier and a date — and
none was in the register before this pass:

| entry | the rule | ratifier and date in the record |
|---|---|---|
| D-249 | The whole decision surface is delivered as user-visible text before any choice question | user mandate 2026-07-05 |
| D-250 | Dispatches are written only when they are next; a parked instruction is revalidated first | not stated |
| D-251 | A running dispatch is never interrupted or steered mid-flight | user, 2026-07-05 |
| D-252 | One side writes the instruction files and the other executes them, never the reverse | not stated |
| D-253 | Working-tree files are read with the file tools; shell access is limited to git object queries by explicit hash | user mandate 2026-06-21 |
| D-254 | Investigate by default; never ask the user whether to investigate or proceed | user mandate 2026-06-14 |

Each is entered `home_is_layer_spec: false`, `nonspec_kind: "unhomed"` — **recorded only on a
tracking surface** — which is [[OI-240]]'s own classification: a session handoff block is a place
for tracking work, not a home for a standing decision.

## What this says about the phase-1 homing pass

The homing acts drove the register's tracking-surface-only count to **0**. That zero was true of
the 231 entries the register then held; it was not true of the repository. Adding these six moves
the count 0 → 6. The homing pass is not wrong — it homed what it was given — but the count cannot
be read as "no standing decision is left on a tracking surface" until the enumeration behind it is
itself complete.

`CLAUDE.md` already treats this surface as carrying standing rules: its provenance paragraph names
"the ⛔ TOTAL UNIFICATION rule (`cowork_handoff.md`)" among the "companion standing rules
elsewhere". So the question these six raise is not whether they bind — they plainly do — but
whether a handover document is their home, and if not, which specification is.

## Disposition

**For the NEXT homing wave, not for this pass.** The residual second pass may not edit
`ARCHITECTURE.md` (its dispatch forbids it) and may not ratify a decision. What is owed:

1. The user ratifies (or corrects) the six register entries — they are in the pass report's
   ratification queue.
2. The homing act itself: decide the owning home for each. Candidates the record already suggests
   are `CLAUDE.md` (which holds the project's other standing process rules, register group T) and
   `cowork_design_doc_template.md` (the ratified home of the writing standards) — the choice is a
   decision, not a mechanical move, so it is not made here.
3. Whether "recorded only on a tracking surface" is even the right classification for a rule that
   governs the working protocol rather than the system is a question for the user: the register
   already distinguishes a **decision about the process, correctly homed** (26 entries) from an
   **unhomed** one, and the line between them was drawn when the only process rules in the register
   lived in `CLAUDE.md`.
