# OI-297 — `tools/audit/process_check.py` truncates its own findings list on a Windows console

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Process / audit tooling. CC-found 2026-08-03 (phase 1o, Task 5), running the check the dispatch
ordered over its own text.**

## What happens

`process_check.py` writes its JSON artifact first and then prints the findings to stdout, quoting
each finding's sentence. On a Windows console the default encoding is `cp1252`, and the print raises
`UnicodeEncodeError` at the first sentence carrying a character outside it — in this instance `→`,
which appears in the phase-1o dispatch's own premise-ledger lines. The process ends with a traceback
and a non-zero exit after having printed a **prefix** of the findings.

Observed here: the artifact records five findings; stdout showed three and then the traceback.

## Why it is more than cosmetic

The visible symptom is a short list plus a traceback. A reader who takes the printed lines for the
whole result **under-counts the findings** — a search that reports fewer misses than it made, which
is the shape #19 exists against. The non-zero exit is also indistinguishable, from the outside, from
the check having failed for a substantive reason.

## What is not at risk

The artifact is written **before** the print and is complete; and a report cites the artifact rather
than the console output (D-431), so no recorded figure anywhere is affected. The check's own
establishment artifact regenerated byte-identically in the same session, so its measured detection
power and false-positive rate are unmoved.

## What the fix looks like, and why it is not made here

One stream wrapper (`errors="replace"`) on stdout, or printing from the artifact rather than from
the in-memory rows. Either is small — and under **D-436** a mechanism is trusted only with a measured
detection rate and a measured false-positive rate, so the change carries a re-establishment run like
every other member of the set. The phase-1o dispatch licenses the tooling its own tasks build and
nothing else, so this is rowed rather than fixed.

## What is NOT in doubt

That the artifact is complete; that the five findings it records are what the check found; and that
four of the five are the section-reference false-positive class the phase-1s wave already measured
and published rather than tuned away.

**★ Dated note — 2026-08-03 (CC, phase 1u, Task 5): CLASSIFIED as a known limit, and the class is
WIDER than this one tool.**

**The classification, on the user's direction:** this is a **print-encoding matter, not a check
defect.** The distinction is the one that decides how it is treated. What the check FINDS is
unaffected — the artifact is written before the print and is complete, and a report cites the
artifact rather than the console (**D-431**), so no recorded figure anywhere is wrong. What is
affected is the console rendering of a complete result. The tool's measured detection power and
false-positive rate are therefore not in question, and it is not a mechanism failing one of
**D-436**'s three conditions.

**The class is wider, measured this wave.** The same failure was hit twice more while running
ordinary inspection commands over repository text — a `UnicodeEncodeError` on `cp1252` at the first
character outside it, aborting the output after a prefix. **It is not specific to
`process_check.py`; it reaches any tool in `tools/audit/` that prints repository prose to a Windows
console**, and repository prose is full of the characters that trigger it (`→`, `★`, `—`, the
typographic quotes). The two tools built this wave —
`tools/audit/gen_ratification_surface_set.py` and
`tools/audit/reaim_ratification_surface_paths.py` — therefore print **ASCII only**, and say so in
their source, so the class does not grow while it is open.

**What this changes about the fix:** it should be applied once across the set rather than to this
one tool — a stream wrapper at the point of printing, or printing through the artifact. Under
**D-436 as amended** (a mechanism failing a condition is REPORTED, not automatically removed) the
change still owes its own measurement, but nothing here is a reason to distrust the tool in the
meantime.

## Dated note — 2026-08-03 (CC, phase 1w): two further members, one of them a tool the class had not been measured on

Running the guard set for phase 1w, the class fired twice more.

- **`tools/audit/decisions/gen_home_classification.py --check`** crashed printing a MINUS SIGN
  (U+2212) in its per-document movement lines, after completing the classification and printing the
  totals. **This one matters more than a cosmetic crash:** the lines it did not reach are the
  `STALE vs the files:` findings, so on a Windows console the check exits non-zero having printed a
  clean-looking summary and none of what it found. The findings were recovered by re-running with
  `PYTHONIOENCODING=utf-8` and are rowed as [[OI-305]].
- **`tools/audit/process_check.py`** again, on a RIGHTWARDS ARROW inside a quoted dispatch sentence
  — the same tool, a different character, and a reminder that an ASCII-only *fix* has to cover
  quoted input text, not only the tool's own literals.

**What the second instance adds to the diagnosis:** the phase-1u note recorded that both tools built
that wave print ASCII only *and say so in their source*, which stops the class growing among NEW
tools. It does not help a tool that prints text it read from a file. The single fix named above — a
stream wrapper, or printing through the artifact — covers both; an author-side discipline does not.

## Dated note — 2026-08-03 (CC, phase 1x, Task 1): FIXED once for the class, established, and the diagnosis was wrong about where it happens

**The shared cause, checked before anything rested on it (the dispatch's assumption A2).** Both
crashes are the same `UnicodeEncodeError` from the same `cp1252` encoder on the same stream. The
CHARACTER SOURCES differ and that difference is the whole reason an author-side remedy could not close
it: `gen_home_classification.py` died on a MINUS SIGN in its **own format string**, while
`process_check.py` died on a RIGHTWARDS ARROW in **text it had read from a file**. The phase-1u remedy
— new tools print ASCII only and say so in their source — closes the first and cannot close the second.
**A2 HOLDS**, and a stream-level fix closes both.

**One correction of diagnosis: it is not "on a Windows console".** Measured here, the failing stream is
one that is **not** a console — `sys.stdout.isatty()` is false and the encoding is `cp1252` when output
is piped, redirected or captured. On a real console handle Python already uses UTF-8. So the failure
fires exactly when someone is CAPTURING the output — a log, a redirect, an agent harness — which is
worse than the row's original framing, not better.

**The fix.** `tools/audit/output_encoding.py`, one module, one function, imported by the guard set
(#6). It reconfigures the standard streams to UTF-8 with `backslashreplace` and does nothing else: no
exception handling around anyone's print, no exit code touched. `backslashreplace` rather than
`replace` because an escape says which character was dropped and a question mark does not (#12).

**Established, not asserted** — `tools/audit/output_encoding_establishment.json`, four probes, each a
real child process with its stdout piped, which is the failing condition rather than a simulation of
it. Two measure that the fix removes the crash (the unfixed child truncates and dies; the fixed one
prints every line and every probe character). **Two measure that it removes nothing else**, which is
the half the dispatch singled out — *a guard that now prints but no longer fails is worse than one that
fails invisibly*: a child that exits 1 still exits 1, and an unrelated exception still raises, still
prints its traceback, still ends the process.

**★ THE FINDING NOBODY WAS LOOKING FOR: the fix already existed, hand-copied into about seventy tools.**
`sys.stdout.reconfigure(encoding="utf-8", errors="replace")` appears at the top of ~70 files across
`tools/` — and the `tools/audit/` checks are, with two exceptions, the ones written **without** the
copy. That is why these particular tools crashed: not a new problem, an old solution that was never
unified (#6). `register_lint.py` carried its own copy and now routes through the module;
`tools/open_items_split_check.py` carries a PARTIAL copy (`errors="replace"` without the encoding), so
it does not crash but silently mangles — visible in this session's run as `OVERALL PASS ? bijection
holds`, an em dash turned into a question mark. **The wider sweep across `tools/` is NOT done here** and
is the remaining scope of this row.

**What this changes about the row's status:** the class is closed for the guard set, which is what made
[[OI-305]] and [[OI-309]] findable at all. It is not closed for `tools/` at large.
