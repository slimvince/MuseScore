# OI-235 — §4.1's "keep the vertical/contextual boundary clean" prohibition is contradicted by the contextual scoring the same section specifies

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section B — Layer 4 / decision-conformance. Found by the [[OI-207]] adjudication, 2026-08-01.
Registers a NON-CONFORMANCE against decision D-060 in `DECISIONS.md`.**

## The decision

`ARCHITECTURE.md:1855-1859` and `:1877-1879`, the §4.1 design boundary. Verbatim:

> `RuleBasedChordAnalyzer` is a **vertical sonority analyzer**: it identifies what chord
> is implied by the set of simultaneously sounding notes at a single point in time. It
> does not perform functional harmonic analysis (Roman-numeral reductions, cadence
> detection, tonicization, secondary dominants) or contextual annotation (what role this
> chord plays in the surrounding progression).

> Do not
> attempt to improve corpus agreement by adding heuristics to `RuleBasedChordAnalyzer`
> that embed contextual assumptions — keep the vertical/contextual boundary clean.

## What the same document specifies

`ARCHITECTURE.md:1631-1632`, §4.1b, verbatim:

> **Solution:** Contextual bonuses applied only to non-bass-root Major/Minor candidates,
> using information from neighbouring chords.

`ARCHITECTURE.md:1772-1779`, §4.1d, verbatim in part:

> The core scoring loop in `RuleBasedChordAnalyzer::analyzeChord` enumerates
> `(bass candidate, root, template)` triples and applies a set of contextual
> bonuses layered on top of the base template score.

The §4.1g gate table (`:1912-1927`) then lists gates **B**, **C**, **D**, **E**, **F**, **G-B/C/D**
and **H-B/C/D**, every one of whose stated condition is a fact about a neighbouring chord —
`context.nextRootPc == altRoot && bassIsStepwiseToNext` (gate B), `altRoot in recentRootPcs`
(gate C), `consecutiveBassStepwiseCount ≥ 2` (gate D). The §4.1d bonus table (`:1783-1787`) adds
`w_stepIn` / `w_stepOut` (bass motion from the previous and to the next chord), `w_seq` (the next
chord's root a descending fifth away) and `w_dim` (the next chord's root a semitone away — the
condition is named "leading-tone" in the table itself).

These are contextual assumptions about the surrounding progression, embedded in
`RuleBasedChordAnalyzer`, improving corpus agreement. That is the thing the prohibition names.

## What is actually at issue

This is **not** a claim that the bonuses are wrong. They are individually justified, each with a
measured effect, and several are load-bearing (Iter 46 alone moved BIR=false 177 → 128,
`ARCHITECTURE.md:1941-1942`). The finding is that **a prohibition and its violation sit in the same
specification, both stated as current, with nothing reconciling them** — so the specification cannot
be used to decide whether a *new* contextual bonus is admissible. A future session reading §4.1's
design boundary would decline a change that the §4.1d table shows is standard practice; a session
reading §4.1d would add one that §4.1's boundary forbids.

The architecture already names the mechanism by which this happens. `ARCHITECTURE.md:657-659`
(register entry D-036), verbatim:

> When a feedforward layer acquires many gates
> and guards to compensate for missing upstream feedback, that is a symptom of missing
> iteration — not a sign that the layer needs more gates.

and §4.1i restates it as a standing concern at `:2131-2136` ("collectively they are becoming harder
to reason about holistically"). So the contradiction is a *documented* symptom, never reconciled into
a single statement of what the layer is allowed to do.

## Scope note — this is about the legacy scorer

`RuleBasedChordAnalyzer` is on the legacy arm, dormant on both production surfaces since the notation
switch and awaiting deletion at the [[OI-180]] retirement map. The row is filed anyway for two
reasons: the legacy arm is still selectable by an explicit flag and still runs in the test suites; and
the *decision* — where the boundary between a vertical reading and a contextual one sits — is not
retired by deleting the code that broke it. The joint estimator draws that boundary somewhere too,
and nothing in the record says where.

## Disposition

Either (a) the §4.1 design-boundary prohibition is annotated with the class of contextual evidence
that IS admitted (neighbour root, neighbour bass, stepwise motion) and the boundary restated in terms
of what remains forbidden (Roman numerals, cadence detection, tonicization inside the scorer); or
(b) it is recorded as superseded, naming what superseded it. **Nothing is fixed or edited here.**
