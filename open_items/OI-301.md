# OI-301 — `tools/open_items_split_check.py --split-baseline` overwrites the frozen split reconciliation with a failing report, and nothing warns

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section F — process / audit tooling. CC-found 2026-08-03 (phase 1u, Task 6) by triggering it, and
caught by the standing self-check on the session's own changed-path list.**

## What happens

`tools/open_items_split_check.py` runs in two modes. LIVING mode (the default) is the standing
register-health check and is valid on the current tree at any time. `--split-baseline` is the
**historical** reconciliation of the 2026-07-26 split event: it compares the current index against
the pre-split file at commit `cb246a7580` and asserts that no item was lost or added.

Every item opened since the split — a hundred of them at the time of writing — is by construction an
addition relative to that baseline. So the historical mode now **always fails**, and it writes its
failing report over `open_items/split_reconciliation.json`, the committed artifact `CLAUDE.md`'s
open-items-register section names as the byte-level split reconciliation.

Observed here: the mode was run as part of a routine guard sweep, reported `OVERALL FAIL` listing
all hundred post-baseline items as `added_in_index` and `extra_detail_file`, and replaced the frozen
PASS artifact. It was restored from HEAD in the same session.

## Why it is more than a misuse

The tool behaved exactly as documented, and running the historical mode against a current tree is
a misuse. But three properties make it a hazard rather than an operator error:

1. **The frozen record is the casualty.** The artifact exists to document that the split lost and
   added nothing. A mode that destroys that record on an ordinary invocation destroys the evidence
   for the claim it was written to support (**#12**).
2. **Nothing warns.** There is no message saying the mode is only meaningful at the split baseline,
   and no refusal to overwrite a passing artifact with a failing one.
3. **The failure looks alarming and is not.** `OVERALL FAIL — reconciliation mismatch` over a
   hundred item IDs reads like the register has broken. A session that committed it would leave a
   false alarm in the tree, and a later reader has no way to tell it from a real one.

## What is NOT in doubt

LIVING mode, which is the standing check and passes: the bijection holds, no detail file carries a
status of its own, and every original item stays byte-verbatim. Nothing about the register's health
is in question, and the split itself reconciled correctly when it was performed.

## What the fix looks like

The mode's report should be **derived rather than asserted**: post-baseline items are known (living
mode already computes them and reports them as `post_baseline_ids`), so the historical
reconciliation should exclude them by construction and pass, or it should refuse to run and say the
mode is valid only against the split commit. Either way the artifact must not be overwritten with a
failing report — the safe form is to write only on a pass, or to write to a distinct path and leave
the frozen record alone.

Under **D-436 as amended** the change owes a measured detection rate (it must still catch a genuine
lost or altered original row) and a measured false-positive rate before it is trusted.
