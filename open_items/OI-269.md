# OI-269 — CONFLICT: a standing process lesson says commit pipeline-affecting changes immediately; the governing document says commit only when asked

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section F — doc-sync debt (#10) / conflict between two recorded rules. Found by the phase-1d
enumeration wave, 2026-08-02, reading `docs/iteration_path1_summary.md` in full. Both sides are
quoted; nothing is fixed here.**

## The two sides

`docs/iteration_path1_summary.md:112-116`, under "Process lessons", verbatim:

> - **Commit all changes that affect BIR metrics immediately.** Never leave
>   pipeline-affecting changes in the working tree uncommitted across sessions.
>   The Iter 36 change to `batch_analyze.cpp` was lost to a `git reset --hard`
>   three weeks before being detected, and only the documented baseline (held
>   in a binary in `ninja_build_rel/`) made the loss visible at all.

`CLAUDE.md`, the Conventions section, verbatim:

> - Commit only when explicitly asked

The first is stated as a lesson to carry forward ("this discipline should carry into path 2" is
the neighbouring lesson's wording); the second is a standing instruction in the governing
document, and is registered — it is part of the Conventions block the register carries.

## Why it is a genuine conflict and not merely stale

The document carries **no superseded banner** (checked at HEAD; it is one of the 101 files in the
wave's reading list with no status banner at all — which is itself the [[OI-268]]-adjacent
observation that register entry **D-256**, the status-banner convention, is not universally
applied). Its "Architecture decisions made during this path" section is still cited as live: two of
its five items are registered decisions (D-102 and D-061), and this wave entered two more from it
(**D-280**, gates read structured fields only; **D-281**, the batch tool's alternative-fields
floor). So a reader who reaches this document for those decisions reaches the conflicting lesson on
the way.

The conflict is real but narrow. The governing rule is about **who decides when to commit** (the
user does); the lesson is about **what must not be left uncommitted across a session boundary**
once a commit is made. They can be reconciled — "when a commit is made, pipeline-affecting changes
go in it" — but neither text says so, and as written the lesson instructs a session to commit on
its own judgment, which the governing document forbids.

## The evidence behind the lesson is not in dispute

The failure it records is concrete and is worth keeping whatever the reconciliation: a change to the
measurement tool was lost to a hard reset and went undetected for three weeks, and only a stale
binary holding the documented baseline made the loss visible. That failure is also the recorded
defense of **D-281**.

## Disposition

For the user, as a governing-document question: either annotate the lesson so it reads as "in the
commit the user asks for, nothing pipeline-affecting is left behind" rather than as an instruction
to commit, or supersede-banner the document. **No edit is made here** — `CLAUDE.md` is a governing
document, and a design document's status banner is a statement about that document's standing.
