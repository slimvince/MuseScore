# OI-289 — The 80 LEGACY-marked register entries were swept, never verified; two of them were wrong

## What the mark used to claim, and why the claim is gone

The LEGACY marker is generated text, one fixed sentence rendered on every marked entry
(`tools/audit/decisions/gen_decisions_register.py`, `LEGACY_MARK`). Until 2026-08-03 it ended:

> *…this decision's subject is the dormant pipeline awaiting deletion at the retirement map; **it
> has no effect on the live solution**.*

That last clause is a claim about the LIVE system, and the marking pass never checked it — the set
was drawn by asking what each decision is ABOUT, which is a different question. **It failed twice,
both times on evidence found later:**

- **D-329** (phase 1i) — the complete-candidate-listing decision. Its subject is the legacy scorer,
  but the user's [[OI-275]] ruling carried its PRINCIPLE across to the live family design, so "no
  effect on the live solution" was false of it. The remedy then was a second marker variant (the
  transfer mark), which fixed the instance and left the clause standing on the other entries.
- **D-311** (this wave) — the chord-analyzer file-split sequencing. Its subject is
  `chordanalyzer.cpp`, which `STATUS_ARCHIVE.md:114` records as a file that *"SURVIVES the
  engagement; R9 splits `chordanalyzer.cpp`, does not delete it"*, and one of the five translation
  units the split produced, `chordsymbolformatter.cpp`, is run by the record arm at
  `notationimplodebridge.cpp:1170`. Neither the old clause NOR the weakened sentence is true of it.

**The user ruled the clause removed rather than re-argued** (option C3 of the phase-1m dispatch): a
swept population with two demonstrated errors is not established (#19), and a mark that asserts more
than the pass behind it checked is a claim under load with nothing holding it. The mark now states
only what the decision is ABOUT. Executed in the GENERATOR, so one change covers every marked entry
and the wording cannot drift between them (#17f).

## What this row carries

**The full re-verification of the marked set against a live-reachability test.** As of the weakening
the set is **80 entries** (81 before D-311's mark was removed on the established evidence above —
which is a correction of a demonstrated error, not a sweep, and is the only per-entry change made
without the verification this row calls for).

*The 80 is counted from the data, and no figure in the record matches it.* `STATUS.md`'s phase-1i
entry says **75**; the register's own ratified preamble says **79**
(`DECISIONS.md`, the eighth ratification event); the phase-1m dispatch says **75**. The 75/79 pair
is an internal inconsistency dating from phase 1i itself; the growth from there is the marked
entries among D-406…D-426. Sizing this row's work from any of the three would under-count it, so the
count is stated here as derived and a reader should re-derive rather than quote — the same failure
shape [[OI-283]] rows for the register's coverage claim. The test is the one the D-311 and D-329 failures show
is needed: for each marked entry, is its subject reachable on either production surface at HEAD, and
does any ruling carry its principle across to the live design?

**Note that the phase-1m finding on the P4 fallback may bear on a whole CLASS of them, not just on
D-311.** [[OI-288]] establishes that the legacy notation arm's reachability is decided by one runtime
flag whose default is `true` (`composingconfiguration.cpp:178`) and by four branch points, not by
compilation — so "dormant" is a statement about a default, with an enumerated false-negative path
(an explicit flag flip, `batch_analyze` without `--joint-inference`, the test suites, and the
declared non-production uncached path). Any per-entry verdict has to say which of those it means.

## What is NOT in doubt

The marking convention itself (user-ratified 2026-08-02, `CLAUDE.md` decisions-register rule (f)) and
its purpose: a reader must never mistake a ruling about soon-deleted code for one about the live
solution. Nothing in this row weakens that. What it withdraws is an unchecked assertion that rode
along with it.
