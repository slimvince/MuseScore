**Section D — the record-arm interactive path (notation)**

**The user's report (2026-07-27, running the switched build `2a81af273e`):** selecting anything
in a score renders NO visual highlight; the status bar DOES show what is selected (note, range,
…), and annotating the (invisible) selection with chords/Romans acts on exactly what was
selected — so selection STATE and the annotate path work; only the visual highlight is gone.
Additionally, spacebar does not start/stop playback.

**Candidate mechanisms — HYPOTHESES, not findings (the never-guess rule):**

(a) **The OI-203 latency escalated from annoyance to functional breakage.** The note-seam
funnel (`analyzeHarmonicContextAtTick`) runs one whole-score `produceNotationRecord` per query,
synchronously; the status-bar/accessibility path fires on every selection change. If that runs
on the UI thread at seconds-scale per event, paint (the highlight) and input dispatch (the
spacebar shortcut) starve. Corroboration already on record (OI-203's dated note): the
record-arm golden run is markedly slower at test scale for exactly this reason. Against this
hypothesis: the user reports the highlight NEVER appears (not late) and spacebar stays dead
(not laggy) — persistent rather than transient starvation would need something re-triggering
the decode continuously (accessibility polling? repeated selection-changed events?) — to be
measured, not assumed.

(b) **An exception escaping the record-arm funnel mid-handler**, aborting the
selection-visuals chain downstream of the status-bar hook. The producer's designed failure
mode is an explicit `ok=false` with nothing written, but an UNCAUGHT throw from deeper (the
adapter on a score feature the corpus never exercised — tuplets, grace notes, multi-measure
rests, linked staves…) would not be that designed path. The user's score's features are
unknown; the corpus establishment covered chorale-shaped scores.

**The disposition path (investigate-by-default; no fix design before the mechanism is
measured):** the diagnosis dispatch — reproduce on the user's scenario; instrument the
selection-changed → status-bar path (timing + exception trap); determine whether the funnel
fires once or repeatedly per selection event; identify the exact blocking/aborting site. Only
then the fix decision surface (candidates, depending on mechanism: async/deferred status-bar
computation — a presentation-layer concern; the OI-203 keyed record cache; an exception
barrier at the funnel with the designed failure state; each with alternatives per the standing
rule).

**Mitigation available NOW (the designed escape):** explicit `useJointNotationRecord = false`
selects the dormant legacy arm — the revert escape the switch deliberately preserved. This is
also why this row BLOCKS the OI-180 retirement map: the legacy arm must not be deleted while
this regression is undiagnosed.

**Dated refinement (user, second field report, 2026-07-27):** the symptoms sharpen decisively —

presents as "renders late." **Mechanism fit (hypothesis (a) strongly corroborated, (b)
disfavored):** the quick paths never invoke the harmonic status-bar query; the single-note

queuing a fresh whole-score decode. (b) is disfavored — the highlight renders, late, so
nothing aborts the chain. **Still owed before the fix decision surface:** the in-flight
Task-1 measurement + a call-path confirmation (the funnel is the only slow-path invoker; one
decode per event, no re-trigger loop) — then the fix alternatives (the OI-203 keyed record
cache; and/or moving the status-bar computation off the interactive thread — a
presentation-layer concern) come as a decision surface with numbers.
