## The question

Two pieces of the legacy chord path have a fire rate nobody has measured on the repertoire the
requirement names:

1. **The P4 tick-local fallback** — `analyzeHarmonicContextLocallyAtTick`
   (`notationcomposingbridge.cpp:621`), which runs the legacy trio `findTemporalContext` (`:651`),
   `analyzeChord` (`:656`) and `applyIter8691Pedal` (`:663`). The only figure in the record is the
   comment beside its call site: *"P4 fallback (cold findTemporalContext, unchanged). **Fires
   0/2231 on the perf corpus**"* (`:750-752`).
2. **The Layer-1.5→Layer-4 fact cycle** — `findTemporalContext`
   (`regiontoneprimitives.cpp:452`), which instantiates a chord analyzer and runs a full
   `analyzeChord` + `applyIter8691Pedal` + `applyPostScoringGates` on each neighbour segment
   (`:507-520`, `:565-578`). [[OI-165]] records it as *"not currently scheduled to die"*.

## What the code says — and why this row's framing is not the one it was dispatched with

The phase-1m dispatch held that the P4 fallback is **reachable on the live notation arm**, and asked
for its fire rate on that basis. **The code refutes the reachability half, and the correction is
recorded here rather than carried forward.**

`analyzeHarmonicContextAtTick` (`notationcomposingbridge.cpp:703`) branches on the record flag
FIRST: `:726-739` returns `buildNoteContextFromRecord(...)` — or an empty context on a produce
failure — whenever `prefs->useJointNotationRecord()` is true, and that setting defaults **true**
(`composingconfiguration.cpp:178`). The regional path (`:743`) and the P4 fallback (`:753`) sit
BELOW that return. They are reached only on the legacy arm. The function's other caller of
`analyzeHarmonicContextLocallyAtTick`, at `:789`, is inside
`analyzeHarmonicContextAtTickUncachedForTesting`, which `:760` declares *"NOT the production path"*.
The same holds for the fact cycle: both of `findTemporalContext`'s production call sites —
`regionanalyzer.cpp:921` and `notationcomposingbridge.cpp:651` — are on the legacy arm.

So **the "0/2231" figure is not a measurement about the live arm at all.** It measures how often P4
fires *given that the legacy arm ran*, on a performance corpus. Two separate things were being
conflated: whether the branch is reachable (a control-flow question, now answered) and how often it
fires when reached (a repertoire question, still open).

## What is therefore still worth measuring, and why it is not nothing

**(a) The fire rate within the legacy arm, on real repertoire.** [[OI-215]]'s lesson is that a
branch measured dead on the fit population can be live on the repertoire the requirement names, and
a zero count on one corpus is not an establishment (#19). The 23 committed large scores are the
population that would answer it. This bears on what the retirement map deletes and on how much
behaviour rides on a path scheduled for deletion — a smaller stake than the dispatch supposed, and
stated as such.

**(b) ★ The sharper half: is [[OI-165]]'s own reading still true?** That row says the Layer-1.5
primitive is *"not currently scheduled to die"* — but both of its production call sites are on the
legacy arm, which the retirement map's R1/R5/R6 delete (**D-418**). Either the row's premise is
stale, or the primitive has a future consumer the row does not name. This is not a fire-rate
question and does not wait for a corpus run; it is a reachability-and-ownership question that
[[OI-165]] itself now owes an answer to. It matters beyond bookkeeping, because register entry
**D-428** (the iteration-API renames) is classified as debt on *partly-live* code precisely because
`regiontoneprimitives.cpp` is held to survive.

## What is NOT in doubt

The three call facts the dispatch cites (`:651`, `:656`, `:663`) are correct, and the P4 comment
says what it says. What was wrong was the conclusion drawn from them about the live arm.
