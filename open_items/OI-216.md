# OI-216 — The C++ joint decode is std::string-keyed in its DP hot loop, and appears slower than the pure-Python reference

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — the analysis-cost / notation-surface cluster (decoder cost structure; sealed §S finding S2)**

**The observation (Cowork, at the analysis-cost measurement).** On `bach_chorale_001` (80 events) the
C++ `decodePiece` took **5,650 ms** (`large_score_decode_profile.json`), while the pure-Python
reference — memoization OFF — means **3,415 ms** at 77.7 events (`window_study.json` cost curve). The
build is `RelWithDebInfo /O2 /Ob1 /DNDEBUG` (a debug build is excluded), so a compiled C++ decode being
~1.65× SLOWER than interpreted Python is a #3 surprise: a native port of a hot numeric loop is expected
to be faster, not slower.

**The cost-structural mechanism (CC-confirmed at the code, OI-199 pass 1).** The semi-Markov DP
(`jointdecoder.cpp:732-836`) is **`std::string`-keyed throughout its hottest loop**: per candidate per
window per boundary it constructs `stateEnc(tonic,major,ckey)` (`:820`), the `content()` cache key
`std::to_string(i)+","+std::to_string(j)+","+stateEnc(...)` (`:659`), the `candidates()` cache key
(`:651`), `keyEnc` (`:793`), and `StateEntry::backEnc` is a `std::string`; all are keyed into
`std::unordered_map<std::string, …>` (`bh.idx`, `contentCache`, `candCache`, `kchg`, `perClass`,
`summ`). Each is a heap allocation + a string hash in the innermost loop — plausibly the dominant
per-candidate cost, and exactly the kind of thing a Python dict (which interns/space-optimizes small
string keys and hashes them once) pays less for relative to naive `std::string` construction. Cowork's
unconfirmed hypothesis (the string state) is thus **structurally supported by the code**; the DIRECTION
of the comparison (C++ slower) is Cowork's timing measurement — CC did not re-measure the timing this
pass.

**Not a correctness matter.** The decode is `probe_decoder`-parity-correct (bit-identical on the pinned
corpus). This is purely a cost/representation concern: the state key could be a packed integer / tuple
rather than a formatted `std::string`, removing the per-candidate allocation + string hash. **Declared
to Cowork; NOT acted on** (OI-199 is read-only; any refactor is a performance-design decision at its
#8-correct stage, and it is OI-199's own subject matter — the review reviews the joint module, of which
this is part). Related: [[OI-215]] (the same decoder's robustness cliff), [[OI-217]] (the fact-build's
super-linearity, the other half of the cost picture), [[OI-203]]/[[OI-206]] (the interactive latency
this cost feeds).
