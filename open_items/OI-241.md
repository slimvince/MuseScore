## What does not exist

**Nothing states which MuseScore interfaces the bridge layer itself may call.** The bridge is by
construction the place engraving types are touched (D-072/D-228), and the document says what shape
its functions take and where they live — but not, for example:

- whether the bridge must go through `INotationInteraction` and the property system, or may read
  the score model directly (the distinction §19.2 draws for the language model at
  `ARCHITECTURE.md:6392-6396` — what the user deliberately set, versus what the engraving engine
  derived — is stated for that module only);
- whether layout-derived state is off limits to analysis input at all;
- what happens when a needed MuseScore behaviour has no public interface (the two do-not-revert
  local patches, `CLAUDE.md:629-677`, are both edits to MuseScore's own code — a *dependency* on
  existing MuseScore code of a fourth kind entirely, and no rule governs when that is admissible).

The last is the sharpest: the record contains two instances of the practice and no rule for it, one
of which carries a permanent distribution constraint (`CLAUDE.md:679-685`, fork-local, never
upstream) that sits beside a recorded long-term intent to contribute the work officially
(`ARCHITECTURE.md:328-330`). Both positions are registered and cross-linked in `DECISIONS.md`
(D-117 and D-197); neither states how the general intent is discharged given the exception.

## Why this is the user's call

A missing ruling is not a defect to be fixed by inference. Naming which MuseScore interfaces are
permitted, and when editing MuseScore's own code is admissible, is a scope-and-contribution
judgement with a licensing dimension — not a rule application.

**Dated note — 2026-08-02 (Cowork): RULED by the user — the rule ADOPTED as proposed** (presented
with stricter/looser/defer alternatives rated on the principles and the objective; adopted as
recommended). The rule: (1) the analysis library depends on no MuseScore or engraving types (the
standing Dependency Rule); (2) the bridge layer reads the score model only through the
established bridge pattern and never layout-derived state as analysis input — the Layer-1 note
model is the single sanctioned reading surface for analysis facts (OI-98 is henceforth judged
against this); (3) editing MuseScore's own code is admissible only for a feature-blocking defect,
each instance recorded in the local-patches section with a per-instance distribution disposition
(upstreamable or fork-local) ratified by the user — reconciling the §1.2 contribution intent
(D-117) with the fork-local patch constraint (D-197). Written into `ARCHITECTURE.md` §3.3
(`:969-995`) and registered as **D-229** in the ruling's commit (the D-230 same-commit rule
honored on its first day).
