# OI-214 — The embedded tables are stored as JSON text and parsed per call (a decision record with an undeclared cost)

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — the analysis-cost / notation-surface cluster (decision record; undeclared runtime cost)**

**The fact.** The joint estimator's production tables/adapter/weights are compiled in as **JSON text**,
not a parsed-structure codegen: `jointembeddedartifacts.h` states they are embedded "VERBATIM (JSON
bytes, not a parsed-structure codegen) and parsed at load through the SAME parser as the filesystem
path", and `jointnotationproducer.cpp:37-40` states they are "loaded fresh per call (a shared/cached
loader is a later, measured concern)". So every `produceNotationRecord` re-parses the embedded JSON
(`JointTables::loadEmbedded("all")` + `FittedAdapter::loadEmbedded`) — phase 2 of the four-phase decode.

**Why it is a decision record, not a defect.** Ratified Decision D1 said "compiled-in constant data"
without settling the FORM. The verbatim-bytes-plus-shared-parser form was chosen in Cowork's codegen
dispatch on two principled grounds: **carried-forward establishment** (#19 — the embedded bytes are
byte-identical to, and parse through the same path as, the established filesystem artifacts, so no new
parse path needs establishing) and **one parse path per concern** (#6). Both are sound. What was never
done is **declare or measure its runtime cost** — the per-call re-parse.

**The measurement.** The analysis-cost dispatch's phase profile (Task 1) times phase 2 (the embedded
table/adapter/weight load) separately, per score, so the per-call parse cost is now a measured figure
rather than an unexamined "later concern". Cowork's prior prediction (recorded before measuring) was that
the parse is immaterial (single-digit milliseconds) relative to the decode; this row is the home for the
measured answer. If phase 2 is immaterial the decision stands unchanged with its cost now declared; if it
is material at scale (e.g. relative to a bounded-window decode) it becomes an input to the [[OI-203]]
cache design (a shared/cached loader was always named as the deferred option). Related: [[OI-212]] (the
whole-score decode this parse precedes), [[OI-209]] (the large-score regime where per-call fixed costs
matter more relative to a bounded decode).

*Provenance: the form was chosen in Cowork's codegen dispatch (carried-forward-establishment + one-parse-
path grounds); its cost was never declared or measured. Rowed by CC at the analysis-cost dispatch's Task
0, 2026-07-28; the phase-2 measurement is `tools/notation_seams/large_score_decode_profile.json`.*
