# OI-208 — The decisions register: rulings need the same one-home treatment issues got

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section F — docs / process (#6 applied to decisions)**

Proposed by Cowork 2026-07-27 at OI-207's rowing; user ratification of the shape owed.

**The root cause it fixes:** the 3.1b contradiction happened structurally, not carelessly-once:
(1) the 2026-07-18 doc split moved decision history into `STATUS_ARCHIVE.md` /
`cowork_handoff_archive.md`, both explicitly OUTSIDE the session-start read ("reference-only");
(2) the project has a register for ISSUES (`OPEN_ITEMS.md` — created because 91 items were
scattered over 12 surfaces) but NO register for DECISIONS — a ratification, a
shelving-with-evidence, or a falsification has no living surface a later dispatch is forced to
consult; it binds only as long as someone remembers it. The constrained-optimum ledger
corollary records alternatives per decision, but inside per-decision documents that also age
into archives.

**The proposal (the OPEN_ITEMS pattern applied to rulings):** one lean DECISIONS index — per
row: the decision (plain words), date, who ratified, STATUS (live / superseded-by /
shelved-with-evidence / falsified), the evidence pointer, the detail link — with per-decision
detail files where the row's pointer does not suffice; populated initially from OI-207's
enumeration; added to the session-start read (CLAUDE.md); and rule (c)'s analogue: a new
ratification/shelving/falsification gets its index row IN the commit that records it. A
dispatch that touches a decision's subject must cite its row — the mechanical habit that would
have surfaced 3.1b before the seams dispatches specified whole-score.

**Bound:** the index stays lean (the register-split lesson — descriptions 1–2 sentences,
narrative in detail files/the cited documents); the living-mode coherence check pattern
(`open_items_split_check.py`) extends to it if warranted.

**Dated note — 2026-07-28 (CC, the decision-harvest dispatch): the population INPUT is delivered in
this register's field shape.** The harvest (`tools/audit/decisions/decision_candidates.json`/`.csv`)
emits each candidate in exactly the shape this register would consume, so the later pass populates a
register rather than writing prose: **id** (`DH-…`) · **decision_text** (the author's own words,
verbatim) · **date** · **ratified_by** · **status** (LEFT EMPTY — this register's live /
superseded-by / shelved-with-evidence / falsified) · **conformance** (LEFT EMPTY) · **evidence_pointer**
(commit hashes, document names, `OI-…` refs, artifact paths auto-extracted) · **source_occurrences**
(this occurrence + every linked repetition; repetitions are LINKED, never dropped — repetition is
evidence of standing). The `manifest.json` is stamped to the corpus git hash + the instrument blob sha
(#16). When the user ratifies this register's shape, the initial rows are a mechanical projection of the
`status`/`conformance`-empty candidates the OI-207 adjudication has filled.

**★ SHAPE RATIFIED (user, 2026-07-28) — three rulings.**

1. **The register holds WHAT WAS DECIDED, and its status. Nothing else.** The proposed
   `conformance` field is REMOVED. Rationale (the user's, recorded): a decision's status changes
   only when someone rules again; whether the code obeys it changes every time the code moves.
   Holding both in one row produces a register that silently goes stale — the exact failure the
   issue register was created to end. **Non-conformance is tracked in `OPEN_ITEMS.md` as ordinary
   rows**, each pointing back at the decision it violates. One home per concern, each with its own
   clock (#6).
2. **A decision belongs, wherever possible, in the OWNING LAYER'S SPECIFICATION** — that layer's
   section of `ARCHITECTURE.md` — and the register is the **index and pointer**, never a
   substitute home. This follows the standing rule that the layer specification is the primary
   place decisions about how a layer should work are recorded (`CLAUDE.md` Conventions,
   2026-07-28). **Consequence for the adjudication:** a decision whose proper home is a layer
   specification and which is not recorded there is a **documentation gap → an `OPEN_ITEMS.md`
   row**, distinct from a non-conformance row. The register entry then points at the specification
   section, not at a scattered restatement.
3. **The register is CLEAN — one entry per decision, not one per occurrence.** The harvest's
   15,224 candidates are occurrences; roughly 57 % are Claude Code session reports restating
   rulings made elsewhere. Consolidation to the distinct decisions, each with its authoritative
   home identified and its repetitions linked as evidence of standing, is the adjudication's first
   task and the precondition for the register being readable at all.

**Dated note — 2026-07-28 (CC, the decision-clustering dispatch): the clustering LAYER exists, and it
carries a STOP for ruling 3.** `tools/audit/decisions/gen_decision_clusters.py` (a sibling of the
harvest, one tool per concern — #6) emits `decision_clusters.json`/`.csv` + `cluster_manifest.json` as a
layer OVER `decision_candidates.json`, which it never writes. Signal 1 (near-identical text: Jaccard on
word 3-gram shingles, threshold **0.80**, statements under 8 tokens matched by exact text only) FORMS the
clusters; signals 2 (shared evidence pointer) and 3 (same date + ratifier) are emitted as links BETWEEN
clusters and merged nothing, per their declared weaker/weakest strength. **Non-destructive, proven:**
all 15,224 candidates present, each in exactly one cluster, input sha256 unchanged
(`gen_decision_clusters.py --check`). **Established (#19), exactly:** `--check` plus `--establish`
(`cluster_establishment.json`) brute-forces the EXACT similarity of every pair of the 13,894
similarity-eligible units sharing a shingle — **93 exact pairs at/above 0.70, 93 found, 0 missed, 0
spurious; recall and precision 1.0000.**

**★ THE STOP (#13) — ruling 3's premise does not hold at the harvest's unit granularity.** The ratified
shape assumes the 15,224 occurrences consolidate to a readable number of distinct decisions. They do not
consolidate MECHANICALLY: **the clustering yields 14,460 clusters — 14,274 of them singletons.** The
cause is diagnosed, not guessed: **this repository restates decisions by PARAPHRASE, not by copying**, so
whole-unit wording similarity cannot reach them. Corpus-wide there are only **93** near-identical pairs at
all, almost all repeated layout or dispatch instruction text; the threshold is not the cause (the whole
0.70–0.95 sweep spans 79 clusters in 14,460). The worked counter-example is this project's own leading
case: **46 candidate statements about the Stage-3.1b shelving fall into 46 clusters — every one a
singleton** (`worked_counter_example` in the artifacts). **Consequence for the adjudication: the cluster
count is NOT the decision count; it is the count of distinctly-worded statements.** Ruling 3's
consolidation therefore remains judgment work in full — it was not reduced by this pass. What the pass
DOES deliver: a labelled **boilerplate bucket** (74 clusters / 373 occurrences — recurring headings and
table header rows, and the standing push/stop/read-only dispatch instruction lines; KEPT, not deleted, so
the judgment is confirmable a class at a time), **6 clusters flagged internally divergent** (5 outside the
bucket) left unresolved by design, 1,876 evidence-pointer link groups and 52 date+ratifier link groups,
and a proposed representative per cluster chosen by SOURCE AUTHORITY alone. **No adjudication was done:
status, conformance and supersession are untouched.** The user-facing worked preview of ruling 1/2/3's
entry shape is `tools/audit/decisions/cluster_preview.md` — **awaiting the user's read**. Not worked
around: changing the unit (sentence-level splitting) or matching by meaning are method changes with their
own risks and were not in this dispatch's scope.
