# OI-309 — Four generated artifacts in the decisions chain do not re-derive at the committed tree

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — instrument / measurement layer. Rowed 2026-08-03 (CC, phase 1x, Task 2), running every
guard with the visibility fix in place and deriving the guard list from what exists.**

## What fails

Four checks report drift. Their complete output is at `tools/audit/guard_state.json` → `runs`, and
nothing is restated here (**D-431**):

- `gen_phase1p_delegation_bar.py --check` — `phase1p_delegation_bar.json` does not re-derive
- `gen_phase1n_reading_regime.py --check` — `phase1n_reading_regime.json` does not re-derive
- `gen_phase1m_measurements.py --check` — `phase1m_measurements.json` does not re-derive
- `gen_phase1g_triage.py --check` — `phase1g_triage.md` differs from a fresh generation

## Pre-existing, and how that was established

**Not caused by phase 1x, and not by phase 1w's uncommitted work.** Each of the four derives from
`backbone_decisions.json`, `decision_clusters.json`, `cluster_dispositions.json` and a set of design
documents; **none of them reads a `.py` file's content or line numbers**, and none reads `OPEN_ITEMS.md`,
the `open_items/` files or `STATUS.md` (their mentions of those surfaces are all in docstrings). The
changed-path list for this session and for phase 1w — taken through `tools/audit/changed_paths.py` —
contains none of their inputs.

**Which wave introduced each is NOT established.** Establishing it means bisecting each artifact against
the history of its inputs, which this wave did not do; the honest statement is that it is unknown, not
that it is recent.

## Why they went unnoticed, which is the part worth keeping

This is [[OI-305]]'s finding widened. That row recorded that the home-classification check "is not in
the guard list any recent wave reported running", and named phases 1v, 1u, 1s and 1r as each having
enumerated a guard list that did not contain it. The same is true of all four here. **The guard list
lived in prose, one wave at a time**, and prose notices neither an addition nor an omission — which is
why this wave built `tools/audit/gen_guard_state.py`, whose candidate population is derived from what
exists and whose authored invocations STOP on a candidate they do not cover.

**And until this wave the failures could have been invisible even when run**: the checks print their
findings after writing their artifacts, and a character outside `cp1252` ended the process mid-list
([[OI-297]]). That is fixed at `tools/audit/output_encoding.py`, which is why this is the first run in
the arc whose completeness can be relied on.

## Why nothing was fixed

The phase-1x dispatch's Task 2 forbids it in terms: fixing what the task finds would be acting before
the extent is known. Each of the four also needs the same diagnosis [[OI-305]] asks for and does not
answer — whether the artifact is **stale** (regenerate it) or **historical** (a frozen record of what a
past pass found, which regenerating would destroy, the [[OI-301]] hazard). `gen_phase1p_delegation_bar.py`
is the clearest candidate for the second reading: its own docstring says it "IS A PRE-APPLY RECORD, AND IT
STAYS ONE", and it deliberately reads frozen fields so that re-running cannot overwrite the finding it
carries. An artifact that is *meant* not to reproduce needs a mode that says so, not a regeneration.

## What is NOT in doubt

That the four checks ran and reported; that their output is complete; and that the register's own two
guards — `gen_decisions_register.py --check` and `gen_cluster_dispositions.py --verify` — PASS, so the
rendered register matches its data and every entry's verbatim quote is at its cited home.

**Dated note — 2026-08-04 (CC, READ WAVE 1, `cc_instruction_reads_1.md`): one of the four artifacts
was TOUCHED by this wave, and the touch is declared here so a later diagnosis is not misled.**

`gen_phase1p_delegation_bar.py --check` still reports the same one line it reported before —
*"STALE vs the files: phase1p_delegation_bar.json does not re-derive"* — and the verdict is
unchanged. But **part of the drift is now this wave's**: five documents became somebody's home for
the first time when the wave entered its register entries, and that tool's `FORMS` table STOPS on a
home document with no authored grade, so five grades were added
(`docs/llm_integration.md`, `cowork_layer6_grouping_design.md` and `cowork_target_architecture.md`
graded **bare-appended-citation**; `cowork_factorization_desk_simulation.md` and
`docs/layer_architecture_audit.md` **named in none of the three ratified surfaces**; all five
EXCLUDE, so no section-kind judgment is reached).

**Why this sharpens rather than muddies the diagnosis this row asks for.** The row records that
`gen_phase1p_delegation_bar.py` is *"the clearest candidate"* for the HISTORICAL reading — its own
docstring says it *"IS A PRE-APPLY RECORD, AND IT STAYS ONE"*. This wave is the first demonstration
of the consequence: **a pre-apply record cannot hold a live grade table.** Every read wave that homes
an entry in a new document must add a grade, because the tool refuses to run without one — so the
LIVE half of that file will keep moving while the artifact it emits is supposed to be frozen at
phase 1p. Whatever mode is chosen, it has to separate the frozen finding from the grade table the
classifier imports, and the two are in one file today.

The other three artifacts (`gen_phase1n_reading_regime.py`, `gen_phase1m_measurements.py`,
`gen_phase1g_triage.py`) were **not** touched by this wave and their reports are unchanged
— deliberately, for the reason at [[OI-316]].
