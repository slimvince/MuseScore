# OI-238 — §5.13's analyze-at-tick path table predates the record arm: it asserts "no path-selection flag" while a flag selects between two arms, and does not list the record branch

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section F — doc-sync debt (#10), DT-12. Found by the [[OI-207]] adjudication, 2026-08-01.
Sibling of [[OI-232]]; filed separately because it falsifies a table a reader uses to find code, not
a status claim.**

## The statement

`ARCHITECTURE.md:3688-3690`, verbatim:

> Every entry point that runs harmonic analysis against a tick position is listed here.
> All analyze-at-tick paths go through a single classical path; there is no Jazz path,
> no path-selection flag, and no symbol reading anywhere in the analysis pipeline.

The clause it was written to make — *no Jazz path, no symbol reading* — is still true and is a real
decision (register entry D-067). The clause **"no path-selection flag"** is not.

## What is there now

`notationcomposingbridge.cpp:728-738` — the single funnel `analyzeHarmonicContextAtTick` branches on
a flag and returns from the record arm before any legacy code is reached:

> `        if (prefs && prefs->useJointNotationRecord()) {`
> … `            return buildNoteContextFromRecord(rec.record, tick);`

with the flag defaulting ON (`composingconfiguration.cpp:178`). So there **is** a path-selection flag,
it is the production default, and the table's seven-row entry-point list (`:3694-3702`) describes the
arm that is *not* running.

## The second, sharper consequence

The table's `analyzeHarmonicRhythm(score, start, end, …)` row is the only place a reader is told that
an analyze-at-tick path takes a **time range**. On the record arm no such narrowing exists — the
funnel produces a whole-score record and looks the tick up in it (register entry D-011,
`ARCHITECTURE.md:114`). A reader consulting §5.13 to learn what a tick query costs, or what music it
reads, is told the opposite of what the shipped path does. That is the same input-scope question
[[OI-212]] tracks on the span seams, arriving on the note seam through a stale table rather than
through a decision.

## A third item this table also settles, and should record

`ARCHITECTURE.md:1284-1301` (register entry D-063, "D-P4") makes the tick-local cold-context fallback
"the **current contract**, documented and accepted", with a stated revisit trigger:

> Stage 3 design **must** state explicitly what P4 (and the bridge) consume
> from the decode.

Two things are now true and neither is written down: the joint/record design never stated it, and on
the switched build the P4 fallback (`analyzeHarmonicContextLocallyAtTick`) is **unreachable from the
production funnel** — the record arm returns first. The function survives as a direct call from the
pipeline-snapshot suite only (`pipeline_snapshot_tests.cpp:569`), which is why the switch
reconciliation could report the `tickLocal` golden section byte-identical: it is measuring a path
production no longer takes. So D-063 governs nothing on the shipped product, and the golden section
named after it protects nothing that ships.

## Disposition

Correct §5.13's three claims (the flag clause, the entry-point list, the time-range row), and add a
sentence recording the P4 fallback's actual reachability so the snapshot section's coverage is not
over-read. **No code change.** To run with the other `ARCHITECTURE.md` corrections ([[OI-232]] /
[[OI-233]] / [[OI-236]]). **Nothing is edited here.**
