# OI-239 — The joint fact adapter re-implements the Layer-2 boundary rule with three behavioural differences, and no layer specification records that it does

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — joint module / #6 total unification + documentation gap. Found by the [[OI-207]]
adjudication, 2026-08-01. Bears on decisions D-041 … D-050 in `DECISIONS.md` (the Layer-2
specification) and on D-023 (the constant-sonority slice as the atomic analysis unit).**

## The ratified rule

`ARCHITECTURE.md:1045`, the Layer-2 specification, verbatim in part:

> `changePointSlices(noteModel)` returns an ordered, **covering, lossless** list of half-open
> `[start,end)` spans that **tile the domain with no gaps and no overlaps**. Boundaries = the
> sorted-unique union of every **onset AND every release** of the **eligible** notes; consecutive
> boundaries form the slices.

with three further stated properties: eligibility is read from Layer 1 and **never re-decided**
(`:1047-1049`); the domain is **clipped to the loaded span** and slicing "never drags outside" it
(`:1055-1060`); and an interior stretch where every eligible voice rests is an **explicit EMPTY
slice, not a gap** (`:1063-1065`).

## The second implementation

`jointfactadapter.cpp:456-490` computes its own lattice. Verbatim, the comment and the boundary
construction:

> `    // ── the event lattice (gen_note_events.extract_stem): minimal segments between consecutive`
> `    // notated onsets/offsets with >=1 sounding note (the Pardo & Birmingham partition) ────────────`
> `    std::set<int> boundSet;`
> `    for (const NoteRec& n : notes) {`
> `        boundSet.insert(n.onset);`
> `        boundSet.insert(n.onset + n.dur);`
> `    }`

**The boundary rule itself agrees** with Layer 2: every onset and every offset. That is the finding's
good news and is worth recording, because it means the segmentation unit conforms.

Three properties do not agree:

1. **Eligibility.** Layer 2 admits a note to boundary generation only if Layer 1 flagged it
   `plays && visible && staffEligible`, and forbids re-deciding that (D-045). The adapter's `notes`
   set is built from the `notatedNotes()` surface with the adapter's own inclusion rules; there is no
   corresponding statement of what it admits, and no specification says whether the two sets are the
   same.
2. **Silence.** Layer 2 emits an explicit empty slice (D-049). The adapter skips it —
   `jointfactadapter.cpp:479-481`, verbatim: `if (!anySounding) { continue; // a silent gap is not a
   harmonic event }`. Defensible for a harmonic decode, and stated at the site; but it is a
   *different* answer to a question a layer specification already decided, recorded only in a code
   comment.
3. **Clipping to the loaded span.** Layer 2's clip rule and its re-slice-equivalence guarantee
   (D-050, `ARCHITECTURE.md:1055-1070`) have no counterpart in the adapter, which decodes the whole
   score (register entry D-011). This is the mechanism side of [[OI-212]].

## Why this is filed as one row and not folded into an existing one

[[OI-228]] is about the **note set the emission reads within an event** (struck versus sounding).
This row is about **who computes the events at all** and under which rules. They are adjacent — both
are the joint module answering a question Layer 2 already answered — but they are separable: fixing
the emission to read the sounding set would leave the duplicate boundary computation exactly where it
is, and unifying the boundary computation would not by itself change what the emission reads.

The documentation half is the sharper half. `ARCHITECTURE.md:15` names "the **event lattice** +
exact block-factorized semi-Markov Viterbi decoder" and never states the lattice's rule; the Layer-2
section states a rule for a slicer the production decode does not call. So the canonical document
specifies a boundary rule that is not the one running, and does not specify the one that is.

## Disposition

Two separable acts, neither done here:

- **Documentation:** record the joint module's event-lattice rule in a layer specification, including
  the three differences above and the reason for each — the [[OI-237]] Kind-1 pattern.
- **Structure (#6/#7):** decide whether the two boundary computations unify, and if so which way. This
  is a Premise-Gate decision surface at its #8-correct stage, and it belongs with the
  [[OI-215]] / [[OI-226]] / [[OI-227]] / [[OI-228]] family design, not before it — the family's
  governing question is where the joint module's input surface is specified, and this is another face
  of it.
