**The finding (CC, OI-199 pass 1).** The committed audit inventories under
`tools/audit/{l1l2,l3,l4,l5}/` were frozen at their audit commits (`7123c7cb55` / `9e294f398d` /
`7f57aad4b5` / `940632ecd1`). HEAD `5135764ed7` is far past them — the whole joint-estimator arc + the
notation switch landed in between — so regenerating any prior layer at HEAD produces different deep-CSVs.
This is **pure source drift**, not a tooling regression: e.g. `note_model.{cpp,h}` gained 126 lines since
the l1l2 freeze, and the deep files of every layer changed. PROVEN not to be the OI-199 tooling change —
the OI-199 `gen_inventory.py` edit reproduces byte-for-byte the output of a minimal tool = HEAD's tool +
ONLY the joint base rule, on all four prior layers (deep-CSVs AND file_tables identical); the extraction
engine functions were untouched.

**Disposition.** This is the exact **OI-95** shape ("the committed L1/L2 inventory artifacts are
line-stale") one level up — now a whole-file-set drift, not just line numbers, because the source moved
through a major arc. The frozen inventories remain valid AS FROZEN REFERENCES pinned to their commits
(that is what a frozen reference is); they are simply not a current picture of HEAD. **NOT re-baselined
here** — re-baselining another audit's frozen reference is out of OI-199's scope (OI-199 is read-only,
and each layer's inventory belongs to that layer's audit). Recorded so the staleness is tracked, not
silently relied on: if a future session needs a current L1–L5 inventory it must regenerate, not read the
committed CSVs. Related: [[OI-95]] (the founding line-drift instance), [[OI-199]] (the review that
surfaced it). DT-12 (stale reference).
