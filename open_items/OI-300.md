# OI-300 — The shell-read guard owes a false-deny establishment run over two shapes its corpora do not contain

**Section F — process / mechanisation debt (#19). Rowed 2026-08-03 at phase 1u on the user's ruling

## The two shapes

Both were measured live on real commands during phase 1o and are recorded at [[OI-292]]'s dated
note of 2026-08-03. Neither is in `shell_read_guard.py`'s `SANCTIONED` or `FORBIDDEN` corpus, so
the rates published at `tools/audit/shell_read_guard_establishment.json` do not bound the guard's
behaviour on either.

**(1) A MISS — `ls <repository path>` is a real D-253 violation the guard does not deny.** D-253
sends existence reads of the working tree to the file tools in terms: *"Local file content,
existence, line counts and searches always go through the file tools."* The guard's forbidden set
is the named text utilities plus, since phase 1s, `git status`. `ls` is in neither, so an existence
enumeration through the shell passes. This is the same shape as the phase-1r `git status
--porcelain` instance — the guard behaving exactly as built, and the rule broken anyway.

**(2) A FALSE DENY — a path outside the repository, reached through an unexpanded shell variable.**
`tail "$SC/guards1.txt"`, where `$SC` holds the session scratchpad directory outside the working
tree, was DENIED with the working-tree message. The guard reads arguments literally and cannot
resolve a shell variable, so `$SC/...` is indistinguishable from a repository-relative path. The
rule it enforces is about working-tree files, and a scratchpad file is not one.

Note the two are opposite errors. (1) is a gap in coverage; (2) is the guard firing on legitimate
work — which is the condition **D-436** singles out with its own reason: *one that fires on
legitimate work gets switched off, which is worse than having none.*

**(3) A SECOND MISS, of a different command family, found by this wave's own standing self-check.**
`git diff --stat -- <working-tree path>`, issued with no commit hash, was not denied. D-253 permits
git only for read-only OBJECT queries named by an explicit hash, because a content-addressed read is
self-verifying; a working-tree diff is not one. The guard cannot catch it as built — `git diff` is
not a text utility, and the guard's git exemption keys on the PRESENCE of a hash rather than on its
absence, so a hashless invocation falls through both tests. Recorded at [[OI-292]]'s dated note of
2026-08-03 together with two further `ls` instances of shape (1). The sanctioned answer exists:
`tools/audit/changed_paths.py`.

## Why neither is fixed by editing the guard now

Adding `ls` to the forbidden set is a change whose cost is exactly what has not been measured. `ls`
is a common command, and denying a common command is how a guard becomes something a session works
around rather than something it obeys. The phase-1s lesson is on the record in the guard's own
source: `git status` became deniable **only once `tools/audit/changed_paths.py` existed** to answer
the question it was being used for, so the denial stopped firing on legitimate work. For `ls`, the
sanctioned answer does exist (`Glob`), so the case for denying is real — but the run that would
measure the false-deny cost has not been done, and adding it without that run is precisely what
D-436 forbids.

Shape (2) is not an addition to the denied set at all; it is an existing deny that should not
happen. Its fix (recognizing an unexpanded variable as unresolvable, and treating unresolvable
paths as out of scope rather than in) also changes the guard's behaviour, and also owes a measured
rate before it is trusted — for the same reason, in the other direction: a rule that stops denying a
whole argument shape could stop denying real violations wearing that shape.

## What the establishment run must contain

Both corpora extended in one act, and both figures published before and after, the way the phase-1s
tokenizer fix was:

- **`FORBIDDEN` gains the existence-listing forms** — `ls`, `ls -la`, `dir` and their
  repository-path arguments — so the detection rate measures them.
- **`FORBIDDEN` gains the hashless git working-tree reads** — `git diff -- <path>`,
  `git diff --stat` with no revision — tested on the ABSENCE of a hash, which is the property that
  distinguishes them from the object queries D-253 permits.
- **`SANCTIONED` gains the legitimate shapes each fix could break** — an unexpanded variable
  pointing outside the tree; an existence listing of a directory outside the tree; every
  hash-bearing `git show` / `git cat-file` / `git diff <shaA> <shaB>` form the rule explicitly
  permits, which the third fix must not start denying; and the build, test and measurement commands
  `BUILD_AND_TEST.md` mandates, which are not reads at all and must never be denied.
- **Both rates re-measured and published either way** under **D-436**, with a stated revert
  condition, as `changes_2026_08_03_phase_1s.the_tokenizer_fix` did.

## What is NOT in doubt

That the guard's currently published rates are correct **for the corpora it holds** — that is not
being questioned, and the two shapes above are recorded as outside those corpora rather than as
errors in them. And that the guard's two standing coverage limits are unaffected by this row: it
still binds the executing side only, and it still verifies that the hook is declared rather than
that it fired ([[OI-292]] limits 1 and 2).
