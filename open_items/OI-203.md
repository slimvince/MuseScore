# OI-203 — Record-arm note-seam latency: whole-score decode per interactive query (record cache deferred)

**Section D — Instrument / measurement layer (notation presentation performance)**

Cowork-rowed 2026-07-27 at the note-seam verification, from CC's declared cache disposition
(commit `2d16899734`, dispatch `cc_instruction_notation_noteseam.md` Task 2:
"BYPASSED-WITH-NOTE"). The record arm's single-note funnel (`analyzeHarmonicContextAtTick`,
flag ON) runs `produceNotationRecord` — a whole-score decode (production-scale mean ~3–5 s on
the corpus pieces per the adoption record's timing block) — on every interactive query; the
status bar fires per note selection. The legacy arm serves these queries from the bounded-window
decode cache. This is a genuine interactive-latency regression on the flag-ON path, DECLARED at
the build rather than silently absorbed (the dispatch's explicit duty), and DEFERRED rather than
speculatively fixed (#17: a cache is a later, measured concern — no cache is built before its
need and design are measured).

The named remedy shape: a keyed record cache — the whole-score record is keyable on
(score, change-token) even more simply than the legacy window cache; invalidation rides the
same notation-change hooks the legacy cache uses. Built as its own increment, post-switch,
under measure-before-build (measure the actual interactive latency first; the fix must be
verified at the objects like everything else).

Not a switch blocker: correctness is unaffected (the decode is deterministic; only latency),
and the product is unshipped (the 2026-07-26 scoping ruling). The row exists so the deferral
cannot silently persist (register rule (e)).
