# OI-203 — Record-arm note-seam latency: whole-score decode per interactive query (record cache deferred)

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — Instrument / measurement layer (notation presentation performance)**

Cowork-rowed 2026-07-27 at the note-seam verification, from CC's declared cache disposition
(commit `2d16899734`, dispatch `cc_instruction_notation_noteseam.md` Task 2:
"BYPASSED-WITH-NOTE"). The record arm's single-note funnel (`analyzeHarmonicContextAtTick`,
flag ON) runs `produceNotationRecord` — a whole-score decode (production-scale mean ~3–5 s on
the corpus pieces per the adoption record's timing block) — on every interactive query; the
status bar fires per note selection. The legacy arm serves these queries from the bounded-window
decode cache. This is a genuine interactive-latency regression on the flag-ON path, DECLARED at
the build rather than silently absorbed (the dispatch's explicit duty), and DEFERRED rather than
speculatively fixed (#17: a cache is a later, measured concern — no cache is built before its
need and design are measured).

The named remedy shape: a keyed record cache — the whole-score record is keyable on
(score, change-token) even more simply than the legacy window cache; invalidation rides the
same notation-change hooks the legacy cache uses. Built as its own increment, post-switch,
under measure-before-build (measure the actual interactive latency first; the fix must be
verified at the objects like everything else).

Not a switch blocker: correctness is unaffected (the decode is deterministic; only latency),
and the product is unshipped (the 2026-07-26 scoping ruling). The row exists so the deferral
cannot silently persist (register rule (e)).

**Dated note — POST-SWITCH (CC, 2026-07-27):** the notation switch (dispatch
`cc_instruction_notation_switch.md`, user-ratified 2026-07-27) flipped `useJointNotationRecord`'s
default ON, so the record arm's whole-score-decode-per-interactive-query latency is now on the
**DEFAULT (record) notation path**, not behind an off-by-default flag. The record-cache
increment's priority therefore RISES. It stays measured-then-built (measure the actual
interactive latency first, then design the keyed record cache) as its own post-switch increment —
still NOT a correctness concern and the product still unshipped, so it did not gate the switch.
Corroborating evidence surfaced at the switch: the pipeline-snapshot record-arm golden run is
markedly slower than the legacy run (the tickRegional path runs one whole-score `produceNotationRecord`
per sampled tick), which is exactly this per-query decode cost made visible at test scale.

**Dated MEASUREMENT note (CC, 2026-07-28; `cc_instruction_marginals.md` Task 1 — measurement only, the
cache DESIGN returns to Cowork with these numbers).** The interactive latency is now MEASURED. Instrument:
the read-only `NoteSeamLatency.DISABLED_Sweep` (a sibling of the established `P3PerfBaseline` perf harness
in `pipeline_snapshot_tests.cpp`, reusing the four-size-class `kPerfCorpus`: small SATB chorale → mid piano
→ contrapuntal prelude → sonata movement). Generated artifact (figures live there, #17f):
`tools/notation_seams/noteseam_latency.json` — per score, at the record arm (flag ON): (a) one cold
whole-score `produceNotationRecord`, (b) `analyzeHarmonicContextAtTick` per query (sampled ticks — funnel
≈ one produce + the record lookup), (c) the per-query cost were the record memoized (produce once, then
`noteView` per tick). **The measured shape:** the per-query funnel cost equals the whole-score-produce
cost and is **seconds-scale** (rising with score size across the corpus), while the memoized `noteView`
per-query cost is **sub-microsecond** (at the `steady_clock` resolution floor) — a per-query reduction of
~seven-to-eight orders of magnitude if the record is memoized. The memoization bound the keyed-record-cache
design is judged against is therefore the `noteView` lookup cost (negligible); the produce cost is paid
once per (score, change-token). The row **stays OPEN** — the measurement is delivered; the keyed
(score, change-token) record-cache DESIGN is Cowork's next step with these numbers.

**Bears on OI-206 (the user-reported post-switch interactive regression).** This measurement is the direct
evidence for OI-206 hypothesis (a) — the note-seam funnel running a whole-score decode SYNCHRONOUSLY on the
selection-changed/status-bar path (which fires per note selection) would starve UI paint and input dispatch:
the measured seconds-scale synchronous per-query cost is consistent with that mechanism. Diagnosis and fix
belong to the OI-206 dispatch (Cowork's next, after the marginals dispatch returns); this row supplies the
latency figures, not the OI-206 verdict.
