# OI-292 — Ten `CLAUDE.md` rules could be enforced by a mechanism and are not; the strongest is that no check confirms the four local patches are still present

**Section F — Doc-sync debt (#10). Rowed 2026-08-03 by the phase-1p dispatch's own instruction
(`cc_instruction_phase1p_home_rulings_and_mechanisms.md` §6.4): "A process rule that could be a
mechanism and is not is a **defect** — row it."**

## What was done

Every rule `CLAUDE.md` carries was classified MECHANISM-EXISTS / MECHANISABLE-AND-NOT / KNOWLEDGE.
The population is DERIVED, not searched for: it is every register entry whose home is `CLAUDE.md`,
the register having enumerated that document in full (protocol P1). Only the class of each rule is
authored, and each carries the mechanism that covers it or the ground on which no mechanism can.

The artifact is `tools/audit/claude_md_rule_triage.json`, generated by
`tools/audit/claude_md_rule_triage.py`. Its `totals`, `rules_total` and `the_defect_set` carry the
counts; nothing is transcribed here (**D-431**).

## The defect set

`the_defect_set.ids` names them. They fall into five families:

- **★ The file-tools rule itself — BUILT AT PHASE 1p AND NOT ARMED, which is why it stays in this
  set.** `tools/audit/shell_read_guard.py` is committed and established (8 of 8 forbidden forms
  denied, 0 false denies over this session's real commands). Arming it means one block in
  `.claude/settings.json`, and `.gitignore:112` puts that file outside the record as "Claude Code
  local session state". **A live control existing only in an untracked file is the [[OI-285]] class**
  — a change on disk and not in the record, which no later reader can find and no commit can revert —
  so the guard was deliberately left unarmed rather than switched on invisibly. The arming block is
  written out verbatim in the tool's own docstring. Two things ride with the user's decision: the
  settings watcher may need `/hooks` opened once before a newly added hook fires, and the exec form
  takes an absolute path, so a TRACKED form of the block would need one that is not machine-specific
  — which makes *should `.claude/settings.json` be tracked at all?* a real question rather than
  something to settle by force-adding the file.

- **The four local patches — the strongest candidate, and it is a real exposure.**
  `CLAUDE.md`'s "Local patches — do not revert" section carries four edits to code this project does
  not own, each stated as do-not-revert **against a dependency update**. A dependency update that
  reverts one is exactly the silent failure a check catches and a reader does not: nothing fails, the
  tests pass, and the patched behaviour quietly returns to upstream's. A check that each patch is
  still present in the file it patches is a few lines and has no false-positive mode.
- **Two same-commit rules stated as conditions on a diff.** A scoring change and its documentation
  land together; a new ruling and its register entry land together. Both are stated in exactly the
  form a pre-commit check takes, and the first even names an arithmetic staleness check — the
  template count in the scoring document against `kTemplateCount` — that nothing performs.
- **Two convention checks over prose.** The reserved music-theory vocabulary (the collided words are
  enumerated in the rule itself, and the convention is mechanical: the bare word is musical, every
  non-musical use is qualified), and the no-self-invented-labels rule, which admits only a weak
  candidate-flagging form.
- **Two measurement rules.** That every reported comparison carries its uncertainty (#24) — the
  process check has the adjacent half and not this one — and that a newly acquired corpus enters as
  research material, which the corpus manifest could carry as a tier the gate tooling refuses to
  measure against.

## What is NOT owed

`the_defect_set` is not a build list. Each member needs the same thing every mechanism in this wave
needed before it: an established form (#19) — a measured detection rate against real violations and a
measured false-positive rate on legitimate work — because a guard that fires on legitimate work gets
switched off, which is worse than no guard. The two built at phase 1p carry theirs
(`tools/audit/process_check_establishment.json`, `tools/audit/shell_read_guard_establishment.json`).

## What this triage did NOT do, stated because it is the point of the exercise

**No `CLAUDE.md` text was retired.** The dispatch's governing discipline is that a mechanism must let
us delete something, or it is apparatus growth. Neither mechanism built in this wave retires prose:
the process check makes **D-431** and **D-434** checkable without replacing their statements, and the
shell-read guard would enforce part of **D-253** while the rule's scope, its exemption and its
measured defense must all stay readable. That is recorded in the artifact's `what_was_executed`
rather than glossed, and it is the honest answer to the discipline's question: these mechanisms
remove failure modes, they do not shrink the governing document.

Whether that is a good enough reason to keep them is the user's call, and undoing either is small —
the guard is not armed, and the check is a script nothing depends on.

## ★ One live instance, found by this wave's own standing self-check

Running the self-check over its own diff, the phase-1p session found that **it had itself broken
D-253**: it used `git status --porcelain` to confirm what was staged before committing. The rule
names that command among the ones never trusted for what is current, and permits shell access only
for read-only git object queries by explicit hash.

Two things follow, and both are evidence rather than embarrassment:

1. **The shell-read guard would NOT have caught it**, and that is not a gap in the guard — it is the
   coverage limit the guard states about itself. It covers the TEXT-UTILITY half; the
   branch-tip/index half is deliberately not enforced, because blocking `git status` and `git log`
   would fire on ordinary git use and a guard that fires on legitimate use gets switched off. So the
   instance corroborates the stated limit instead of contradicting it.
2. **It happened in the session building the mechanism against it**, with the rule read in full at
   session start. That is the strongest available argument that the rule needs a mechanism and not a
   reminder — and, equally, that the half left unmechanised stays a matter of discipline.

Recorded here rather than in a new row: it is one instance of this row's own subject, and the honest
place for it is beside the coverage limit it tests.

## Dated note — 2026-08-03 (CC, phase 1r): the guard is ARMED, and the coverage is ONE-SIDED

`tools/audit/guard_armed_check.py` reports **ARMED**: `.claude/settings.json` declares a
`PreToolUse` hook, matcher `Bash|PowerShell`, running `tools/audit/shell_read_guard.py`.

**The row does not close clean, and the reason is #19 — a control believed to be in place and not
in place is worse than none.** Four limits, three of them already stated in the guard's own
docstring and one measured live this wave:

1. **One side only.** The matcher names the CC-side shell tools. The writing side's shell tool
   carries a different name and does not match, so **the file-tools rule (D-253) is enforced on the
   executing side and NOT on the writing side.** It must not be described as enforced, full stop.
2. **Declared, not fired.** The check reads settings files; it cannot observe a running session, and
   the settings watcher only reloads directories that held a settings file at session start.
3. **The text-utility half only.** `git status`, `git log` and `git rev-parse HEAD` are deliberately
   not blocked — blocking them would fire on ordinary git use, and a guard that fires on legitimate
   work gets switched off. **That gap was demonstrated live: a `git status --porcelain` issued by
   the executing side was NOT denied.** The guard behaved exactly as designed and the rule was broken
   anyway, which is the honest measure of what arming did and did not buy.
4. **The configuration is outside the record.** `.gitignore` keeps `.claude/settings.json` untracked,
   which is why the CONTROL is in the record as this check rather than as the settings — the answer
   to this row's own [[OI-285]] objection.

**A FALSE DENY was measured, and it is not covered by the established rate.** The command
`grep -c "^  D-" /tmp/reaim_1r.txt` was denied. The guard splits the command on whitespace, so the
quoted pattern `"^  D-"` becomes two tokens and its second, `D-"`, is read as a repository path. The
SANCTIONED corpus in `shell_read_guard.py --establish` contains no quoted-pattern-with-spaces case,
so **the measured false-deny rate does not bound this shape**. Reported rather than fixed: changing
the guard's tokenizer is a mechanism change this wave was not dispatched to make, and under
**D-436** it would owe its own re-establishment.

## Dated note — 2026-08-03 (CC, phase 1s, Task 1): two of the four limits are closed, and the enumeration tool is what closed one of them

**The sanctioned enumeration exists: `tools/audit/changed_paths.py`** (the user's ruling Y1). It
reports the changed-path list and nothing else, and the property that justifies it is structural
rather than intended: it never opens a file for reading, every git invocation comes from a frozen
table inside the module, every row of that table is a subcommand that emits a status code and a path
and nothing more, and only those two fields reach the output. `diff-tree` is used rather than `show`
for exactly this reason — `git show <blob-sha>` prints the blob and `--name-status` does not suppress
it, while `diff-tree` walks commits and trees only and errors on a blob, so the content path does not
exist rather than being avoided. The one caller-supplied argument is a commit hash, validated against
`^[0-9a-f]{7,40}$`, so no ref and no pathspec can be smuggled through it.

**Why this is not a narrowing of D-253**, recorded with the tool because without it the tool looks
like a wrapper around a forbidden command: the rule's recorded defense is that a stale mount made the
shell return wrong CONTENT while the file tools read the live disk correctly, and the git-object
exemption survives because content-addressed reads are self-verifying. **Both halves are about
content.** A list of which paths changed is not content, so the rule's letter is untouched and what
changed is only that the answer comes from a committed tool.

Established (#19) at `tools/audit/changed_paths_establishment.json`: a throwaway repository, a KNOWN
set of modifications — added, modified, deleted, renamed, untracked — reported exactly at the working
tree, at the index and at a commit; a CLEAN tree reporting nothing, before and after; a ref refused
where a hash is required; an unsanctioned enumeration refused. There is deliberately no `--check`
re-derive mode, because reading the artifact back would be a read-mode open and the structural
property is worth more than the convenience.

**Limit 3 is closed on the `git status` half.** The guard now DENIES `git status`. What changed is
not the reasoning but its premise: the half was left unenforced because blocking it would fire on
ordinary work, and that was true only while no tool answered the question. `git log` and `git
rev-parse HEAD` stay unblocked — nothing replaces them, so the same reasoning still protects them,
and saying so is what keeps this a measured scope rather than a mood.

**The measured FALSE DENY is fixed and re-established.** Segments are now tokenized with `shlex` in
NON-posix mode, so a quoted argument stays one token; non-posix specifically, because posix mode
would consume the backslashes in a Windows path. Under **D-436** the change owes its own measurement,
so both figures are published: `tools/audit/shell_read_guard_establishment.json` →
`changes_2026_08_03_phase_1s.the_tokenizer_fix` carries `false_denies_on_the_sanctioned_set` and
`detection_on_the_forbidden_set` with and without the fix, and the specimen itself is now IN the
sanctioned corpus, so the rate that is published includes the case that produced it. The dispatch's
condition for reverting — a rise in false denies elsewhere — is **not met**.

**Limits 1 and 2 are untouched.** The matcher still names the executing side's shell tools only, so
**the file-tools rule is enforced on one side and must not be described as enforced**; and the armed
check still reports that the hook is DECLARED, never that it fired.

**What is still owed of the defect set:** the eight not built, unchanged. The two closed here were
coverage limits of a mechanism already built, not new mechanisms.
