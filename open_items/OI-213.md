# OI-213 — The addAnalyzedHarmonyToSelection per-note produce multiplier

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — the analysis-cost / notation-surface cluster (per-command cost multiplier)**

**The fact.** `addAnalyzedHarmonyToSelection` (`notationinteraction.cpp:8256`) loops over the selected
notes and calls the note-seam funnel `analyzeNoteHarmonicContext(note, …)` **once per selected note**
(`notationinteraction.cpp:8311`, a loop over `byStaffTick`). On the record arm each funnel call is one
whole-score `produceNotationRecord` ([[OI-212]]), so an **N-note selection costs N whole-score decodes**
per single command.

**Why it matters.** It compounds the [[OI-206]] / [[OI-203]] interactive-latency regression on an
explicit user command (add analyzed harmony over a selection) rather than on a single-note status-bar
query: the whole-score-per-note multiplier turns an add-harmony-to-selection command on a large
orchestral score ([[OI-209]]) into N × (seconds-scale decode). A **keyed record cache** ((score,
change-token) — the [[OI-203]] remedy shape) collapses the N produces to 1 (the note views are
microsecond lookups into the single record). This is a named input to the OI-206 fix decision surface —
the multiplier is exactly what the cache eliminates.

**Not an inference concern.** The N decodes are deterministic and identical (same score, same change
token); the multiplier is pure wasted latency, correctness unaffected, and the product is unshipped (the
2026-07-26 scoping ruling). The call-path fact is committed at
`tools/notation_seams/callpath_facts.json` (q4, the add-analyzed-harmony consumer).
