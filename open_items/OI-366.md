# OI-366 — The shell-read guard's establishment check reports STALE intermittently, while the artifact it checks re-derives byte-identically

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — instrument / measurement layer (the audit's own guard apparatus). Created 2026-08-11
(CC, `cc_instruction_return_continuation_9.md`, Task 0).**

## What was observed, in the order it happened

The batch's opening full guard run — launched before this session edited any file — reported
`tools/audit/shell_read_guard.py --establish --check` **FAILING**, and reported the guard-state
artifact STALE against that run, which is the same fact seen from the other side: the committed
artifact records this tool passing.

Re-run **in isolation immediately afterwards, with nothing else running**, it failed again, printing
its own message: *"STALE: shell_read_guard_establishment.json does not re-derive"*.

It then **passed on five consecutive runs** — three in one shell, one in another, and one more at the
task boundary — with no intervening edit to the tool, to its corpus, or to the artifact.

## What is ESTABLISHED

**The artifact's content is not what moved.** The module was imported in-process and its
`establish()` re-run, and the result was compared against the committed file by **exact string
equality — the same test `--check` itself performs**. They are equal, at equal length, with no
first-differing character. A line-level diff is empty as well, so the equality is not an artifact of
one comparison's normalization.

**The only environment-dependent input in the decision was enumerated, and no member of it can
move.** `code_path_literals` consults `os.path.exists` on quoted literals found inside interpreter
code — that is the whole of what the establishment reads from outside itself. Enumerated over the
entire corpus, every literal that reaches that test resolves either to a permanent repository file
or to something the repository never has. There is no transient member, so the state of the tree
cannot flip a verdict.

## What is NOT established, and is deliberately not asserted

**The cause.** Nothing here diagnoses it, and the failure did not reproduce on demand after the
second observation, so nothing was measured at a failing run.

**One candidate is named and explicitly NOT claimed.** The establishment publishes a CONTROL ARM —
`outside_repo(..., family=False)` — which restores the case-sensitive path comparison so the 2026-08-08
family fix's effect is separable from the corpus extension's (**D-436**). That arm compares against
the module's `ROOT`, and `ROOT` is derived from `__file__`, which Python makes absolute against the
process's own current directory. A differently-cased drive letter reaching `ROOT` would move that
arm's counts **and only that arm's** — which is the right shape for a difference that appears and
disappears between invocations while the family arm stays put. **It is unconfirmed:** one invocation
was measured with `ROOT` upper-cased and the check passed, and no failing invocation's `ROOT` was
captured. Naming it is so the next session starts from a testable statement rather than from the
observation.

## Why it is rowed rather than filed as noise — and what changed since the last time

`cowork_away_returns.md` §2.2 recorded the same tool failing once at the away batch's start on
2026-08-08 and not reproducing, and said in terms: *"It is not asserted to be a defect — a single
non-reproducing exit against a run of clean ones establishes nothing except that it happened."* That
was the right reading of one event.

**Two consecutive failures on a second date change it.** The shape is now recurring rather than
singular, observed at two starts, on two dates, in both a batched and an isolated invocation.

**And what is at stake is an established value.** This guard's measured **deny rate** and
**false-deny rate** are published in its own artifact and are what **D-436**'s third condition judges
a change to this mechanism against; the family ruling of 2026-08-08 turned on them explicitly. A
check that intermittently reports STALE without a content difference means those rates are **not
reproducible on demand**, and #19 refuses to treat as established a value that is merely
unfalsified. It is also the guard that enforces **D-253**, so its own reliability bears on a standing
rule rather than on a report.

## What is NOT in doubt

The guard's live DENYING behaviour, which is a different code path (the hook) and which was exercised
correctly by this very session: it denied a `python -c` carrying a literal repository path, and the
read was redone through the file tools rather than worked around. The corpus, whose rows are data and
were not touched. The committed artifact, which the in-process re-derivation reproduces exactly.
And nothing about the analysis, any measurement of it, any golden, any corpus of scores or anything
in `tools/robust_stop/`.

## What is deliberately NOT done

**Nothing was changed.** The decision function is a mechanism **D-436** reserves to the user, and the
guard family's own ruling fixes the order — corpus rows first, clause second, both rates re-measured
on the same extended corpus, the revert condition governing. Adding a diagnostic that captures a
failing run's `ROOT` would already be a change to the tool, so it is named as the obvious next act
and is not taken.

## Dated note — 2026-08-11 (CC, `cc_instruction_return_continuation_10.md` Task 4): the candidate this row named-but-did-not-assert is ESTABLISHED, and fixed

**The user's Ruling 50** of `cowork_rulings_2026_08_11_tenth_stop.md`: **DIAGNOSIS FIRST**, the
module `ROOT` included, with a STOP between diagnosis and fix and no fix taken on an unverified
candidate. The STOP did not fire.

**How the diagnosis was taken, and the method is the half worth keeping.** This row's own closing
section says that even a diagnostic capturing a failing run's `ROOT` would be a change to the tool,
and it declined to take one. **It did not have to be.** The module was loaded TWICE from its own
file by an ordinary Python import, once under each spelling of the drive letter in its path, and
each load re-ran `establish()` and applied **the same string-equality test `--check` applies**. The
probe lives outside the repository and edits nothing, so the diagnosis was taken **before any guard
file was touched**, which is what the ruling's order requires.

**THE RESULT, in both directions.** The uppercase-drive load re-derives the committed artifact byte
for byte. The lowercase-drive load does not — and the artifact it produces is longer, differing deep
inside it, which is where the control arm's lists live. **So the candidate this row named is the
cause**, and the mechanism is exactly as the row stated it: the family arm normcases both sides and
never saw the difference; the control arm restores the case-sensitive comparison on purpose and
compares against `ROOT` as written; and a lowercase drive letter therefore moved that arm's verdicts
**and only that arm's**.

**THE FIX AND WHAT IT DOES NOT MOVE.** The drive letter is put in ONE case at module load, so `ROOT`
no longer depends on how the process started. **No live verdict moves** — the live hook decides on
the family arm — so the published deny and false-deny rates are the same values they were. What
changes is that they are **reproducible on demand**, which is the whole of what #19 was refusing to
grant them. Verified after the fix by the same probe: both spellings now give the same `ROOT` and
both re-derive.

**What this remark does NOT claim.** That the drive-letter case is what happened at either of the two
observed failures. No failing invocation's `ROOT` was captured when the failures were observed, and
this row said so. What is established is that the candidate **can** produce the reported verdict and
that it no longer can — which is what makes the check reproducible whichever way the two observations
arose.

one family, one act, the corpus rows before the clause ([[OI-355]]). Every value is at
`tools/audit/shell_read_guard_establishment.json` (**D-431**).
