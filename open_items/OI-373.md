`cc_instruction_resume_lapse_records.md`) at the batch's opening full guard run, which was launched
BEFORE this session edited any file.**

## How it was found

Not by looking for it. The dispatch's Task 2 requires the guard set to be run and reported, so the
whole set was run first, unchanged, to establish the state this batch inherits. The runner printed
its per-guard verdicts and then refused.

## What is established, at which object

**The refusal, read at the runner's own output.** `tools/audit/gen_guard_state.py` derives its
candidate population — every `*.py` under `tools/audit/` whose source carries a `--check`,
`--verify` or `--establish` mode — and checks it against its AUTHORED invocation table. A derived
candidate with no authored invocation is a STOP by that tool's own declared rule, in its own words:
*"a derived candidate with no authored invocation. NON-EMPTY IS A STOP: a guard exists that this run
did not cover."* The run prints `STOP: derived candidate(s) with no authored invocation:
['tools/audit/gen_status_archive_pass.py']` and exits non-zero **whatever every member of the set
said**.

**Where the named tool came from, read at the record.** It was created on 2026-08-11 by the
`STATUS.md` archive pass and given a `--check` mode deliberately — `cowork_away_returns.md` records
the reason in its own words, *"It carries a `--check` mode, so the artifact is not an orphan"* — and
the invocation table was not extended in the same act. **The committed `tools/audit/guard_state.json`
already carries it** at `the_population.unclassified_candidates`, so the condition is not hidden;
what is missing is that no open row carries it and no batch record names it.

**The same shape has occurred before and was closed in the same act each time.**
`cowork_away_returns.md` records prior occasions in these very words — *"the guard runner STOPPED
because the new derivation joined the derived candidate population with no authored invocation"* —
and in each the invocation was authored in the act that created the tool; in the two passages this
session read in place, a classification verdict was authored beside it. This is the instance left
standing.

**KEPT APART, because it is a different fact about the same run:** `--check` reports that the
committed artifact does not re-derive at this tree, while **the verdict set is identical to the
committed one** — the same number run, the same number passing, and the one failing tool is the same
one ([[OI-372]]). So what moved is captured output text rather than any verdict. **Which tool's text
moved is NOT diagnosed here**, and no claim is made about it.

## Why it is a row rather than an act

**The classification a member gets is a judgment, not a lookup.** The invocation table records which
flags a guard runs with, and its two neighbouring classes — NOT RUN with a reason about the tool,
and HISTORICAL under the user's R4 ruling of 2026-08-04 — each require a per-tool verdict with its
evidence, authored in a second tool that STOPs if the two disagree. Authoring one is a mechanism
change and **D-436** reserves it. The candidate's own artifact records a pass performed on one date,
which is the shape R4's HISTORICAL class is for — **named as the question, not answered here.**

**And the cost while it stands is stated rather than assumed:** the runner cannot exit 0, so a
session that reports the guard set from the runner's exit code reports a failure that is not a
guard's, and a session that reports it from the artifact's `summary` reports counts taken from a run
whose completeness the same artifact says is unestablished.

## What is NOT claimed

**No invocation is authored and nothing about the guard set is adjusted.** The dispatch admits the
row landing, the cut's re-run, the lapse records and the close, and forbids adjusting anything to
make a guard green.

**No gating verdict.** Whether this row gates is derived from a cut and is never hand-added
([[OI-336]], **D-436**).

**Not in doubt:** the passing verdicts, each of which is its own tool's word; the archive pass's
both-ways proof, which was performed, recorded and re-checked at that time; the committed artifact,
which records the condition honestly; and nothing about the analysis, no measured value, no golden,
no corpus of scores, nothing under `tools/robust_stop/`.

## Dated note — 2026-08-12 (CC, same batch, Task 2): the undiagnosed half is now diagnosed, and it is rowed elsewhere

The section above says of the committed guard artifact not re-deriving that **which tool's text
moved is NOT diagnosed here**. It was true when written and it is superseded the same day, by the
object-level verification of Task 2's own movement claim: the text that moved is
`tools/open_items_split_check.py`'s, whose em dash reaches the artifact as a replacement character
when the child process encodes with the locale codepage rather than UTF-8. It was demonstrated by
running that tool twice at this tree, unedited, with only the interpreter's output encoding changed.

**It is rowed at [[OI-374]] and not absorbed into this row**, because the subject is a different
one: this row is about a guard missing from the runner's invocation table, that one about guards
whose printing the shared encoding module does not reach and about the sentence the runner's own
artifact carries saying it reaches all of them.

**Nothing else in this row is withdrawn.** The verdict-set identity it records stands untouched —
an encoding difference moves captured text and never an exit code — and the unclassified-candidate
STOP this row exists for is unaffected.
