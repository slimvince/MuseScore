# OI-355 — The shell-read guard denies every `sed` and `awk`, wherever they are aimed

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — instrument / measurement layer (the audit's own guard apparatus). Rowed 2026-08-09
(CC, `cc_instruction_return_continuation_2.md`, Task 0).**

## How it was observed

A read of a file in the session scratchpad — a directory **outside the repository** — was denied,
with the reason naming `sed`'s own range script as though it were a repository path:

> `sed` is aimed at a path inside this repository ('40,60p').

**It was reproduced once, deliberately, before being claimed** — a different script, a different
scratchpad file, the same denial. One observation of a guard verdict establishes nothing; two on
different inputs establish the shape.

## The cause, read at the tool

For a POSIX text utility the guard's path candidates are **every non-option token** after the
utility name. Four utilities carry a correction — `grep`, `egrep`, `fgrep`, `rg` — which drops the
FIRST non-option token because it is the search pattern rather than a path.

`sed` and `awk` are in the same utility set and take a **script or program in exactly that
position**, and they carry no such correction. So the script becomes a path candidate. A bare
script such as `'1,2p'` has no drive letter and no leading separator, so it resolves against the
working directory — the repository root — and reads as inside the tree. The command is denied on
that token, before the real file argument is considered at all.

## Two errors, and the second is the one that bites

1. **A non-path token is classified as a path.** On its own this would be harmless where the real
   target is also inside the tree.
2. **The denial is reached without regard to where the command's actual target is.** That is what
   makes it a false denial: the command was aimed outside the repository, where D-253 does not
   reach, and it was refused anyway.

## What this does NOT do

**It never admits a forbidden read.** The whole failure is on the deny side. A `sed` aimed at a
repository path is still denied — correctly, though for the wrong reason, which is worth saying
because a right verdict from a wrong cause is not evidence the cause is sound.

## Why it GATES

By the clause that overrides the documentation test, not by that test. The guard's **published
false-deny rate is an established value** (#19), measured over the establishment corpus. This
shape is not in that corpus, so the rate is a rate over a population that does not contain the
defect. An establishment obligation always gates, whatever its subject — including the tracking and
audit apparatus itself.

There is a second, practical reason the record already states in its own words: a guard that fires
on legitimate work gets switched off, and that is worse than no guard.

already changed to see it. That order is the ruling's and is not a session's to reorder.

**Meanwhile nothing is worked around.** The reads this denial refused were performed with the file
tools, which is what the rule says to do anyway.
