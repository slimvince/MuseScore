# OI-204 — The record producer lacks analysis-input staff exclusion (`excludeStaves`) — chord-track self-feedback risk

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — the record producer's input surface (composing)**

Origin: CC's note-seam report observation (2026-07-27, dispatch
`cc_instruction_notation_noteseam.md`): "the record arm ignores the excludeStaves
(chord-track) param — produceNotationRecord decodes the whole score, whereas the legacy
note-seam excludes chord-track staves from analysis input… uniform across all record consumers
(P3a/P4 behave identically), rooted in the adapter's whole-score decode." CC classed it a
P6-catalogue difference; **Cowork raised the severity at verification:** the legacy
`excludeStaves` is not merely an input-scope preference — it is the guard that keeps the
IMPLODED CHORD TRACK's own notes (a presentation artifact written INTO the score by the
implode emitter) out of the analysis input. On the record arm as built, re-running analysis on
a score whose chord track is already populated would feed the previous run's output back into
the decode — a self-feedback loop. The measured corpus and the adoption record are unaffected
(corpus scores carry no chord tracks), and the pipeline-snapshot fixtures likewise (P6
quantifies this — expected zero difference on the snapshot corpus); the hazard is the in-app
implode use case specifically.

**The layer-correct fix (declared, not built here):** input selection at the record producer /
fact adapter — which staves feed the L1 fact surface is an INPUT-SCOPING parameter of the
producer (`produceNotationRecord(score, excludeStaves)` flowing into `buildAdapterFacts`'s
note-model construction), NOT an inference change and NOT a consumer-side filter (#7: the
producer owns its input surface; a consumer must not post-filter decoded output to fake input
exclusion). The parameter's establishment: byte-identity on empty exclusion sets vs the
current producer (the corpus/parity establishment stands untouched), plus a test with a
populated chord track proving the exclusion.

**Why pre-switch:** the switch makes the record arm the live producer for the implode path;
shipping the switch with the self-feedback hazard undisposed would be building on an unchecked
causal premise about our own input surface (#18). Disposition (fix, or a measured
demonstration that the hazard cannot arise, or an explicit ratified acceptance) is REQUIRED
BEFORE the switch ratification; P6's dual-arm run quantifies the difference class on the
snapshot corpus as evidence.

*Resolution belongs in the INDEX row; dated notes may be appended here.*

**2026-07-27 — RESOLVED (seams-2 P6 Task 1).** The layer-correct fix as declared above was built.
`buildAdapterFacts(score, stem, excludeStaves = {})` gains the input-scoping parameter and skips any
notated note whose owning staff is in the set — INPUT selection at the fact adapter, the layer that owns
its input surface (#7), before the note ever enters the L1 fact view the decode reads; NOT a
consumer-side post-filter, NOT an inference change (the decode/scoring arithmetic is untouched).
`produceNotationRecord(score, stem, excludeStaves = {})` forwards it. Every record-arm seam threads the
SAME exclude set its legacy arm passes at that seam (arm-for-arm input parity): the annotation emitter and
the tuning bridge pass `chordTrackExcludeStaves(score)`; the implode passes its `{treble, bass}` target
pair; the note-seam funnel (`analyzeHarmonicContextAtTick`) passes its own `excludeStaves` parameter.
So a populated chord track's own notes (the implode emitter's presentation artifact) are never fed back
into a re-analysis — the self-feedback loop is closed.

**Establishment (#19), both directions.** (a) Empty-set byte-identity: the empty default skips nothing, so
the batch/corpus path and the three existing producer tests (`CoreMatchesPartsAndReferenceOnCorpusPieces`
on bwv324/bwv362, `ScoreWrapperEqualsFactsPlusCore` on pb_chorale) are unchanged — the corpus/parity
establishment stands untouched. (b) The exclusion proven: the new
`JointProducerTests.ExcludeStavesScopesTheFactSurfaceAndDecode` shows, on `nm_two_staff` (C5 staff 0 / C3
staff 1), that excluding staff 1 removes exactly its notes from the fact surface (midi-48 gone, midi-72
kept), and on `pb_chorale` (4-staff SATB) that excluding the bass staff CHANGES the produced record while
the empty-set produce equals the default produce. End-to-end through the funnel, the note-seam record-arm
tests (`notationnoteseam_record_tests.cpp`) confirm the exclusion fires: on the two populated-chord-track
fixtures the funnel's committed content scores now correctly reflect the excluded input (the test's
reference record was updated to use the same exclusion — arm-for-arm parity). Suites green (composing 1186
/ notation 61 / pipeline-snapshot 13); flag-OFF byte-identical (no golden refresh). P6's dual-arm run
quantifies the input-scoping difference class on the snapshot corpus (expected ZERO — the corpus carries no
chord tracks). Provenance: dispatch `cc_instruction_notation_p6.md` Task 1.
