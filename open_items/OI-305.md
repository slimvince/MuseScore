# OI-305 — `gen_home_classification.py --check` reports STALE at the committed tree

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — instrument / measurement layer. Rowed 2026-08-03 (CC, phase 1w) by running the guard
set the dispatch asks for, deriving the list from what exists rather than from a named list.**

## What the check reports

Two separate failures, printed under the same `STALE vs the files:` heading:

1. **Four `home_section` fields do not re-derive** — D-321, D-322, D-323 and D-324, all homed in
   `docs/scoring_model.md`. The recorded field names a section; re-deriving it from the document's own
   headings and the entry's own cited line yields a different one. That re-derivation is exactly the
   property the register's own preamble claims for the field — *"re-derived by a check, so it cannot
   go stale when a heading moves"* — so the check is doing what it exists for.

2. **`phase1q_reclassification.json` does not re-derive.** This is a different kind of failure: a
   generated artifact that does not reproduce.

## Pre-existing, and how that was established

The check's inputs are `backbone_decisions.json` and the home documents. **This wave modified
neither** — verified through `tools/audit/changed_paths.py`, which reports the changed-path list and
nothing else. Nothing in the phase-1w work touches the decisions data or `docs/scoring_model.md`.

The reason it surfaced now rather than earlier is worth recording: **this check is not in the guard
list any recent wave reported running.** The phase-1v, 1u, 1s and 1r reports each enumerate the
guards they ran — the register `--check`, the disposition `--verify`, the open-items living check,
the local-patches check, the armed-guard check, the partition and non-gating generators — and the
home classification check is in none of them. It was run here only because the dispatch says to
derive the guard list from what exists.

## Why the two halves need separating before either is fixed

A **stale section field is a pointer**, which the non-gating declaration's own line calls apparatus.
A **generated artifact that does not reproduce is a #19 matter**: reproducibility is one of the three
things that positively establish an instrument, and this artifact is the record of a
re-classification pass over the whole home population — the thing a later reader would consult to
learn what moved and why.

It is also possible that the second half is expected: the classification has been re-run and
re-applied since phase 1q (the phase-1r write list moved six documents), so an artifact frozen at
phase 1q may be *meant* not to reproduce against today's authored inputs, exactly as the split
check's `--split-baseline` mode is meant to be historical ([[OI-301]]). **That is a diagnosis, not a
verdict, and it is why this row asks for one rather than for a fix.** If the artifact is historical,
what is owed is the epoch treatment the classifier already uses for its class fields, not a
regeneration that would overwrite the record of what phase 1q found — the [[OI-301]] hazard.

## Why nothing was fixed here

Correcting a register field is action on the decisions register, and the phase-1w dispatch is a
gathering wave whose only licence to act is over a LEGACY mark it establishes wrong. Regenerating the
phase-1q artifact without the diagnosis above risks exactly the [[OI-301]] failure.

Task 6. Cross-ref [[OI-301]] (a historical mode that destroys the record it documents), [[OI-291]]
(the re-classification pass), [[OI-293]] (the write list), [[OI-208]].*

## Note of 2026-08-04 (CC, READ WAVE 6) — this wave CREATED one more instance of this row's class, deliberately and for a stated reason, and declares it rather than leaving it to be found

`tools/audit/gen_guard_classification.py` — written this wave to carry ruling R4's per-tool verdicts
and their evidence — has a `--check` mode, and **it is NOT in the guard list.**

**Why it is excluded, and why the exclusion is not a choice.** It READS the artifact
`gen_guard_state.py` WRITES. Running it inside that run would classify the *previous* run's state,
and capturing its output into the artifact would change the file it had just read — a two-file cycle
with no fixed point. So `gen_guard_state.py` excludes it from the derived population by name,
alongside itself, with that reason recorded in the artifact at
`the_population.not_a_subject_why`.

**What the exclusion costs, stated because this row exists to make that visible.** Nothing runs the
classification's `--check` automatically. If its verdicts and `gen_guard_state.HISTORICAL` drift
apart, or if a tool enters the population with no authored verdict, the STOP that catches either
fires **only when someone runs it** — which is this row's founding finding, one construct later.

**What bounds it, so the statement is not worse than the fact.** Two of the three STOPs are
symmetric and live on the OTHER side as well: `gen_guard_state.py` itself STOPS if `HISTORICAL`
names a tool with no authored invocation, and that side IS in the guard list. What is genuinely
unwatched is the third — a tool entering the population with no authored verdict — and the window is
one wave, because the next wave to add a guard runs the classification to record it.

**Recorded here rather than rowed**, because the subject is exactly this row's — a check in the
record that no guard list runs — and the remedy is one line in a future dispatch (run it after the
guard state, which is the order its own STOP requires anyway) rather than a decision. Both this
session's runs of it are reported in the wave's own report.

*(Cross-ref [[OI-207]]'s READ WAVE 6 note; artifact `tools/audit/guard_classification.json`.)*

## 2026-08-08 (CC, `cc_instruction_away_execution.md` Task 0) — the ruling this row asked for, applied; and two facts found in applying it that this row's own narrative did not carry

**What was done, and by whose act.** The user's Ruling 1 of 2026-08-08
(`cowork_rulings_2026_08_08_pre_away.md`) took the option this row's own diagnosis names — *"the
epoch treatment the classifier already uses for its class fields, not a regeneration that would
overwrite the record of what phase 1q found"* — and applied it one level up, to the artifact.
`phase1q_reclassification.json` is declared HISTORICAL and the classifier never writes it again;
the live derived view moves to `home_classification.json`; a fourth frozen class epoch,
`class_before_the_2026_08_08_apply`, is added on the same construction as the third, so the class
each entry carried between the phase-1r pass and this one is preserved rather than overwritten
(#12). The applying run then ran at HEAD and the check is green. The mechanism change is licensed
by the ruling (**D-436**).

**★ FACT ONE — THIS CHECK HAD NOT REACHED ITS OWN FINDING SINCE 2026-08-07, AND NOTHING SAID SO.**
The first attempt to run the applying pass stopped with *"authored judgment for a document that is
nobody's home: ['docs/unified_analysis_pipeline.md']"* — a STOP that fires before any entry is
classified. The committed `tools/audit/guard_state.json` records that same STOP as this check's
entire output, so it has been firing since the 2026-08-07 owner-rulings wave re-homed that
document's last four entries and retired three other emptied documents but not this one. **Two
consequences follow and both are larger than the miss.** The stale-field report this row is ABOUT
has not been produced by any run since that date, so the counts quoted in this row and in
[[OI-319]] describe an older tree. And [[OI-350]]'s statement that the same check re-derives the
three route-(i) documents' eleven entries as `contract-home` cannot have come from a clean run at
the committed tree. The retirement was completed here — the judgment moved whole into the register
data's own retired block, the same act with the same reason as the three retirement records already
there — and the finding is surfaced in `cowork_away_returns.md` rather than asserted about, because
what the check says once it runs is a measurement.

**★ FACT TWO — THE FILE NAMED FOR PHASE 1Q IS NOT THE PHASE-1Q RECORD, AND THE RECORD SURVIVES
ONLY BECAUSE THE SNAPSHOT WAS TAKEN.** The establishment of 2026-08-04 froze the live artifact and
its snapshot as byte-identical. They are not identical at HEAD, and it is not the snapshot that
moved: the snapshot still hashes to its established value, while the live file has more than one
content across the recent commits. So the applying run has been performed by more than one wave
since the snapshot was taken, rewriting that file each time — which means the rows describing it
as *held un-run* describe the LAST wave rather than the month, and the [[OI-301]] hazard this row
warned of was realized and absorbed by the snapshot rather than avoided. The measurement, taken at
named commits from git objects, is the generated artifact
`tools/audit/decisions/phase1q_record_divergence.json`, and **no value from it is transcribed
here** (**D-431**). The freeze is now enforced by the run itself: the classifier STOPS if the
snapshot no longer hashes to its established value (#19). **What is NOT decided here:** whether the
stale file is restored from the snapshot, renamed for what it holds, or removed. That is a FILING
DECISION about a committed artifact, it is the user's, and it is surfaced rather than taken.

**What is NOT in doubt.** No analysis, no analysis input, no corpus, no measurement of the
analysis, no golden, nothing in `tools/robust_stop/`. No decision's verbatim, home, status or
defense moved: assumption A1 is discharged at `tools/audit/decisions/apply_field_diff.json`, which
reports no field outside the classifier's two intended writes moving, and accounts for the one
top-level movement with the declared act that caused it.

## 2026-08-09 (CC, `cc_instruction_return_continuation.md` Task 0) — the filing question this row's resolution left with the user is answered: the file is REMOVED

**The user ruled it** — Ruling 1 of `cowork_rulings_2026_08_09_return.md`. This changes nothing
about the resolution above; it closes the one thing that resolution deliberately did not take.

**The pre-act check ran first, and it is the whole safety of the act.** Every commit
`tools/audit/decisions/phase1q_record_divergence.json` names as carrying a state of the file was
tested as a git OBJECT by explicit hash, and every one still carries the blob. Nothing became
unreachable by the removal.

**The current arrangement, which is what the record now states.** Two files, one job each: the
**phase-1q record** at the established snapshot, whose bytes the classifier's own STOP re-checks
against the frozen hash on every run (#19); and the **live derived view** at
`home_classification.json`, which carries `the_phase_1r_re_run`, `the_2026_08_08_apply` and
`write_list` unchanged. Every live pointer in the register data and in the open-items rows now
aims at the second; sentences that name the removed file in the PAST tense are left alone, because
they are accurate history.

**Why removal rather than the two alternatives, both recorded (#12).** Restoring the file from the
snapshot would create a second, unguarded copy of the record — which is this row's own divergence
class reopened, since the copy that diverged is exactly the one that had no guard. Renaming it for
what it held would leave an orphan generated artifact with no writer and no consumer, which is
undeclared dormancy. Removal leaves one home per concern (#6) with nothing lost (#12, the
recomputable-collapse clause), since git holds every state.

**What this does NOT do.** It moves no classification, no class field and no entry; it does not
touch the snapshot; and it does not revisit the epoch treatment, which stands as the 2026-08-08
resolution recorded it.
