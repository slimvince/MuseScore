## What the re-pin confirmed, and where it is written

The OI-141 premise re-pin traced every element of that row's design opening against the arm that
ships, and its finding on this row's subject is that `buildAdapterFacts` reads
`staff(0)->keySigEvent(Fraction(0,1))` — **one staff, one moment** — and that the resulting prior
enters the decode **only at the initial segment**, so a later notated signature change never reaches
it. The trace is at `cowork_away_returns.md` §2.20 and §2.22 and is not restated here (#6).

## Why the confirmation is worth recording at the row

**Because the failure it forecloses has already happened once, next door.** [[OI-141]]'s fourth
input — the key decode's mechanism pinned at the code — was traced two weeks before the path it was
traced on stopped being the production arm, and the re-pin established that none of its elements is
on either shipping surface. A finding established at an arm that no longer ships reads, later, as
though it described the one that does; that is what invalidated that input. **This row is not
exposed to it.** Its subject was read at the joint module's own fact adapter when the row was
written, and the re-pin has now confirmed the same construction at the shipping decode's entry — so
a later session cannot set the row aside as a statement about the dormant path.

signature is read on the shipping path. It says nothing about the row's other half — that staff 0 is
read with no eligibility or exclusion check — and silence is not establishment (#19), so that half
stands exactly as the row records it, neither confirmed nor weakened.

**Nothing is fixed and no stage moves.** No code was read into a change and none was edited; no
