# OI-247 — The key-signature prior is read from staff 0 at tick 0 only: mid-score key changes never enter it, and staff 0 is read with no eligibility or exclusion check

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — joint module / input surface (declared to Cowork).**

`jointfactadapter.cpp:358-367`: the signature input to the decode is
`score->staff(0)->keySigEvent(Fraction(0,1))` — one staff, one moment.

Two consequences: (a) a mid-score notated key change never reaches the prior, though the notated
signature is a ratified (weak) evidence source (register entries D-056/D-057) and the legacy path
carries a known re-anchoring gap of its own (OI-94(a) — this row is the joint-module sibling);
(b) staff 0 is read unconditionally — with no `excludeStaves` and no eligibility check, it can be
the program's own chord track or a drum staff, in which case the prior reads a signature from a
surface the analysis input rules exclude. Not fixed here; the input-surface half belongs with the
family design's specification of what the adapter reads, the mid-score half is an inference
completion question at its #8-correct stage.
