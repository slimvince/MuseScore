# OI-352 — The guard classification's own `--check` is run by no guard list

**Section D — instrument / measurement layer (the audit's own guard apparatus). Separated out of

## Where this came from

[[OI-319]]'s subject — that every read wave widened `gen_home_classification.py --check`'s stale
report while the applying run was held — was discharged by the epoch treatment of 2026-08-08. What
remained attached to that row was a **fragment of a different subject**, recorded in its 2026-08-04
dated entry and rowed nowhere. Ruling 2 flips OI-319 and gives the fragment its own row, because a
discharged row left open for something filed under it is the [[OI-283]] shape, and tracking an owed
item in prose only is a #10 violation (open-items register rule (c)).

## The fact, read at the two tools

`tools/audit/gen_guard_state.py` composes its population two ways that check each other: a
**derived** candidate list — every `*.py` under `tools/audit/` whose source carries a `--check`,
`--verify` or `--establish` mode — and an **authored** invocation per guard. It then removes two
files by name, in `NOT_A_SUBJECT`: itself, and `tools/audit/gen_guard_classification.py`.

`tools/audit/gen_guard_classification.py` has a `--check` mode. It is therefore a derived candidate
that is excluded by name, and it carries no authored invocation either — so it is in **no list on
either side**, and no guard sweep runs it.

## The exemption is correct, and is not what this row disputes

Both files state the reason in their own words: the classification READS the artifact the guard
state WRITES. Running it inside that run would classify the previous run's state and then change
the artifact it had just read, and there is no fixed point. The classification's own STOP requires
it to run AFTER the state for the same reason.

**Nothing here proposes removing the exemption.** What the exemption leaves behind is the gap.

## What the gap actually costs

The classification carries three STOPs, and they are the mechanism that keeps a verdict and its
invocation consequence from drifting apart (#6):

- a tool in the guard-state population with **no authored verdict** — the ruling's own per-tool
  condition, made mechanical;
- a **verdict naming a tool the guard state does not carry**;
- a **disagreement** between its `records-a-point-in-time-measurement` set and
  `gen_guard_state.HISTORICAL`, in EITHER direction.

All three fire only when something runs the tool. Since nothing does, whether the committed
`guard_classification.json` still re-derives is established only when a session remembers to run it
by hand — which is exactly the failure mode `gen_guard_state.py`'s own docstring says the guard list
exists against: *the guard list lived in prose, one wave at a time, and prose does not notice an
addition or a deletion.* The recursion exemption puts one tool back into that state.

## What is NOT in doubt

The classification's verdicts, the guard state's own runs, and the recursion exemption's ground.
Nothing about the analysis, its inputs, any corpus of scores, any golden, anything in
`tools/robust_stop/`, or any entry or status in either register.

**This is not an establishment obligation on a published rate.** The classification records verdicts
about which guards re-derive a live invariant; it publishes no measured rate that a reader consults.
So the clause that always gates whatever the subject is not engaged, and the row is ordinary
apparatus.

## What is owed, and why a session may not take it

The remedy is a change to how the guard sweep is COMPOSED — a second runner stage after the state
run, a wrapper that runs the two in the order the classification's STOP already requires, or an
authored entry carrying a declared ordering. Choosing among those is a mechanism change, which
**D-436** reserves to the user.
