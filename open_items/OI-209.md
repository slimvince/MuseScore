# OI-209 — The large-score requirement: very large scores (a Tristan act, a symphony) must be handled

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section D — the analysis-cost / notation-surface cluster (design requirement)**

User-directed 2026-07-28, in the user's own words: **very large scores — a full act of Tristan,
a symphony — MUST be handled, and are expected to be a MORE COMMON use case than the corpora we
hold.** This is a **standing design requirement**, not a defect: every subsequent inference and
notation-surface design is judged against it.

**The collision it names.** The requirement sits against three established facts:
- the joint estimator's ratified **tractability envelope is CHORALE scale** (≈60–150 events, an exact
  §5 semi-Markov decode, with a documented-pruning reserve for larger inputs — never budgeted at the
  fitted weights, [[OI-188]]);
- the fitted corpus is **326 Bach chorales by ONE composer** (single-composer overfitting risk,
  [[OI-39]]; idiom coverage 1/5);
- expansion to **late-romantic through atonal** repertoire is already mandated but unscheduled
  ([[OI-38]] corpus onboarding; the when-question is the user's).

So the requirement is not merely "run on bigger inputs"; it exposes that both the **cost** envelope
(this dispatch's measurement) and the **accuracy** envelope (the ground-truth half, gated on [[OI-38]])
are chorale-shaped, while the target use case is orchestral. The whole-system architecture review's
worst-case (the Tristan stress case, `cowork_architecture_review_2026_07.md` §7, findings F-9…F-15)
is the qualitative companion of this quantitative requirement.

**Its relation to the effort control.** The user's framing (2026-07-28): the effort control is ONE
setting with several dials that must bound the analysis **temporally**, too — but it is too early to
implement, because we do not yet know factually which parts of the inference must be switchable.
Establishing that is what the analysis-cost measurement dispatch
(`cc_instruction_analysis_cost_profile.md`) is for. The user's recorded #17(b) prediction, verbatim:
*"always read the entire score will VERY likely not survive (maybe only under some effort setting =
EXTREME)."* See [[OI-210]] (the analysis-extent question this requirement forces open) and the
whole-system architecture step-back [[OI-200]] (which reads this requirement against the measured
cost ceilings and the public state of the art).
