# OI-299 — The open-items INDEX rows are paragraph-length narratives duplicating their detail files, and a correction reached one and not the other

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section F — doc-sync debt (#10) / #6, one path per concern. Rowed 2026-08-03 at phase 1u on the
user's ruling of the same date (option 3D: rowed with the deferred resolved-row split as ONE
redesign).**

## The finding

`CLAUDE.md`'s open-items-register section says *"Detail lives in `open_items/`; rows here are
pointers, not restatements."* They are not pointers. An INDEX row routinely runs to several hundred
words and restates its detail file's narrative, its evidence and its dated notes.

The cost is measured, not hypothetical. **The phase-1n correction to [[OI-288]] reached the DETAIL
FILE and not the INDEX row, and the INDEX row carried the false citation through five further
waves** — in the surface this register's own rule makes *"the authoritative status surface"*. That
is the restatement problem, inside the register that exists to end restatement elsewhere.

Nothing about that instance was special. Two copies of the same narrative drift the moment one is
corrected, and the index copy is the one a session reads at session start.

## The redesign

**An INDEX row carries status, subject and a pointer. The narrative lives once, in the detail
file.** Concretely: the ID, the one-line name, the layer/gate, the status of record with its
provenance date, and the detail link — with the description column reduced to a single sentence
naming the subject, not summarizing the evidence.

The status of record stays in the INDEX. That is not negotiable and is not what is being changed:
the split's whole point is one status surface, and the detail files carry a sentinel saying they
never hold one.

## Why it is ONE act with the deferred resolved-row split

Both change the shape of the INDEX, both are held by the same guard, and doing them separately
means establishing that guard twice. The resolved-row split — moving ✅ RESOLVED rows out of the
working index into a closed-rows surface — has the same relationship to
`tools/open_items_split_check.py` and the same establishment obligation. They are scheduled as one
redesign with one establishment step (**#19**).

## ★ A premise of the dispatch that ordered this row does not hold, and the row states it rather than carrying it

The dispatch said both halves *"disturb `tools/open_items_split_check.py`, which holds the original
rows byte-verbatim and enforces a bijection, so both need that guard's redesign"*. Read at the tool:

- **The byte-verbatim guarantee is on the DETAIL files, not the INDEX rows.** Living-mode check (c)
  compares `read_detail_row(oid)` — the single row-shaped line inside `open_items/OI-<n>.md` —
  against the pre-split row read from `git show cb246a7580:OPEN_ITEMS.md` (`:184-188`).
- **The INDEX is read for IDs only.** `read_index_ids` matches each line against the row pattern and
  keeps `m.group(1)`, the ID, and nothing else (`:104-112`).

**So shortening the INDEX rows disturbs the byte-verbatim guarantee not at all**, and it keeps the
bijection intact because the IDs stay. The guard as written already permits this half.

**The split half is the one that genuinely disturbs the guard**: moving resolved rows out of
`OPEN_ITEMS.md` breaks check (a), the bijection, because the detail files remain.

Two real constraints the redesign must respect, both from the same reading: a detail file must
contain **exactly one** row-shaped line (`read_detail_row` returns an error on zero or several,
`:125-128`), and a shortened index row must still begin with the `| OI-<n> |` pattern the ID reader
matches.

The correction does not change the ruling, and it does not change that the two halves are one act —
it changes *why*: they are one act because they reshape the same surface and owe one establishment
run, not because both break the same check.

## What is NOT in doubt

That the split's original guarantee is worth keeping: the detail files hold each item's row as it
was written, and #12 is satisfied by that copy regardless of what the index row becomes. The
narrative is not being deleted anywhere — it is being kept in one place instead of two.
