# OI-349 — Does the production record arm satisfy the stabilization precondition the key-area grouping rule is specified to run after, or does the live path group un-stabilized regions?

**Section B — the analysis. Rowed 2026-08-08 (CC, `cc_instruction_document_routes_and_d472.md`,
Task 3) on the user's ruling of 2026-08-08 (Option A), which ordered the question rowed as its own
open item at the moment **D-472** was homed.**

## The question

**D-472** specifies that key areas are grouped by a smoothing pass **over already-stabilized
regions** — the rule names the stabilization as its precondition, not as an incidental neighbour.
An arm check run at the code on 2026-08-07, before any home text was written, came back **MIXED**:

- **The grouping rule is LIVE.** The pass that performs it is shared and is reached on the
  **production record arm** (`sectionrecordadapter.cpp:360`), where the confidence test reads the
  stored per-region exposure flag rather than re-thresholding a confidence field.
- **⚠ The stabilization it names as its precondition is LEGACY-ONLY.** The
  smoothing-and-stabilization step has **one** call site, and that call site is inside the legacy
  arm (`sectionanalyzer.cpp:750`), under a comment naming that block as the one legacy-arm set site.

So one end of a single decision runs on the arm that ships and the other end does not. **The
question this row carries is which of two things is true:**

1. the record arm satisfies the stated precondition **by other means** — the record's own
   segmentation already delivering what the legacy stabilization pass was there to produce, in
   which case the specification's wording is what needs correcting; or
2. the live path **runs the grouping on input its own specification says must be stabilized
   first**, in which case the analysis has a real conformance defect on the production arm.

**Neither is asserted here.** The check that was run establishes the arm split and nothing more; it
did not test what the record arm feeds the grouping pass.

## Why this row GATES

Its subject bears on the analysis — on what the production notation path computes when it groups
key areas, and therefore on which key the annotation emitter writes Roman numerals against. That is
the test `CLAUDE.md`'s non-gating declaration states, and it is answered YES, so the row is not
apparatus and the declaration does not reach it.

## What is owed, and what is NOT decided

What is owed is a **read-only probe**: establish what the record arm actually supplies to the
grouping pass, and compare it against the precondition the specification states. No fix is
authorized by this row, no design, and no inference change.

**The TIMING is explicitly the user's call and is not settled by the ruling that created this row** —
whether the probe runs before phase 2 or inside it. The 2026-08-08 ruling says so in terms.

## What is NOT in doubt

The grouping rule itself is homed and specified — `ARCHITECTURE.md`, the Layer-6 section, with the
arm split stated beside it and each end carrying its citation (#12). The homing act is complete and
this row does not reopen it. No measurement moved, no golden moved, and nothing in
