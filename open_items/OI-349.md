# OI-349 — Does the production record arm satisfy the stabilization precondition the key-area grouping rule is specified to run after, or does the live path group un-stabilized regions?

> STATUS IS AUTHORITATIVE IN THE INDEX (OPEN_ITEMS.md) — this file carries narrative and provenance only and is NEVER the status of record

**Section B — the analysis. Rowed 2026-08-08 (CC, `cc_instruction_document_routes_and_d472.md`,
Task 3) on the user's ruling of 2026-08-08 (Option A), which ordered the question rowed as its own
open item at the moment **D-472** was homed.**

## The question

**D-472** specifies that key areas are grouped by a smoothing pass **over already-stabilized
regions** — the rule names the stabilization as its precondition, not as an incidental neighbour.
An arm check run at the code on 2026-08-07, before any home text was written, came back **MIXED**:

- **The grouping rule is LIVE.** The pass that performs it is shared and is reached on the
  **production record arm** (`sectionrecordadapter.cpp:360`), where the confidence test reads the
  stored per-region exposure flag rather than re-thresholding a confidence field.
- **⚠ The stabilization it names as its precondition is LEGACY-ONLY.** The
  smoothing-and-stabilization step has **one** call site, and that call site is inside the legacy
  arm (`sectionanalyzer.cpp:750`), under a comment naming that block as the one legacy-arm set site.

So one end of a single decision runs on the arm that ships and the other end does not. **The
question this row carries is which of two things is true:**

1. the record arm satisfies the stated precondition **by other means** — the record's own
   segmentation already delivering what the legacy stabilization pass was there to produce, in
   which case the specification's wording is what needs correcting; or
2. the live path **runs the grouping on input its own specification says must be stabilized
   first**, in which case the analysis has a real conformance defect on the production arm.

**Neither is asserted here.** The check that was run establishes the arm split and nothing more; it
did not test what the record arm feeds the grouping pass.

## Why this row GATES

Its subject bears on the analysis — on what the production notation path computes when it groups
key areas, and therefore on which key the annotation emitter writes Roman numerals against. That is
the test `CLAUDE.md`'s non-gating declaration states, and it is answered YES, so the row is not
apparatus and the declaration does not reach it.

## What is owed, and what is NOT decided

What is owed is a **read-only probe**: establish what the record arm actually supplies to the
grouping pass, and compare it against the precondition the specification states. No fix is
authorized by this row, no design, and no inference change.

**The TIMING is explicitly the user's call and is not settled by the ruling that created this row** —
whether the probe runs before phase 2 or inside it. The 2026-08-08 ruling says so in terms.

## What is NOT in doubt

The grouping rule itself is homed and specified — `ARCHITECTURE.md`, the Layer-6 section, with the
arm split stated beside it and each end carrying its citation (#12). The homing act is complete and
this row does not reopen it. No measurement moved, no golden moved, and nothing in
`tools/robust_stop/` moved.

## 2026-08-09 (CC, `cc_instruction_return_continuation.md` Task 1) — the probe has run, and the answer is possibility 1

**The timing question this row reserved to the user is settled** by Ruling 9 of
`cowork_rulings_2026_08_09_return.md`: the probe runs now, read-only, early. Its whole diff is its
own named artifact, `tools/audit/oi349_record_arm_precondition_probe.json`, in which every
file-and-line citation is LOCATED in the file on each run rather than transcribed (**D-431**); no
value from it is restated here, and the prose below states only what the reading establishes.

## The finding: SATISFIED BY OTHER MEANS, and the means is named

**The production record arm does not run the legacy stabilization step, and does not need to.** The
per-segment key it groups on is copied verbatim from the joint decoder's committed segments, and
those segments are the backtracked best full-coverage path of a **dynamic program whose state
carries the key** and whose key transitions are scored by an explicit term with **separate stay and
change branches**. A key change must therefore pay for itself against the content evidence. That is
a smoothing layer over the key sequence, arrived at by optimization rather than by a post-hoc patch.

**The legacy step's other half is supplied natively.** Read at the code, that step has two halves,
and only the first is the precondition **D-472** names:

1. **Layer B**, a one-region key-island smoother — a region whose key differs from the running
   stable key, and whose successor does not agree with it, is OVERWRITTEN with the running key.
2. **A derived-field loop** recomputing degree, keyTonicPc, keyMode and diatonicToKey per region,
   plus a legacy sparse chord-quality refinement (a CHORD concern, outside this precondition).

Half (2) is not a gap on the record arm: those fields are read off the record segment rather than
recomputed. So the whole of what the step produces is accounted for.

**Possibility 2 is therefore refuted: the live path is not grouping un-stabilized regions.**

## One non-equivalence, recorded rather than smoothed over

The two mechanisms do **not** produce identical region key sequences. Layer B erases a one-region
key island unconditionally; the decoder's key-transition term only makes an island expensive, so an
island survives wherever the content evidence outweighs two key changes.

That does not leave the grouping un-preconditioned, and the reason is **D-472**'s own second
clause: the confidence test is what decides whether a divergent region opens a new area, and a
surviving island that is not assertively exposed is grouped into the enclosing area while keeping
its own key for display — which is the rule's stated intent, word for word. But it is a real
behavioural difference between the two arms and is not glossed as equivalence.

## What the reasoning is NOT, so the two joint mechanisms are not conflated

The legacy arm already states this reasoning in its own comment — it makes Layer B inert when the
J-key-iii re-key wiring is on, on the ground that the per-region key is then already a global
decision. **That is a different mechanism**: it is selected by an environment variable, absent by
default, so on the legacy arm Layer B does run. The reasoning transfers to the record arm; the code
path does not.

## What is now owed, and is deliberately NOT done here

**D-472's wording.** Its verbatim says the grouping runs *"over the already-stabilized regions"*,
and its recorded defense says the rule *"leverages the key/mode fields and the stabilization Pass 4
already performed"*. Pass 4 is the legacy arm's. On the arm that ships, the precondition is met by
a different design, so the specification names a mechanism the production path does not run.
Correcting it — at the Layer-6 section that owns the rule, with the register entry's verbatim
re-taken and the former preserved (#12) — is its own act on this row. The batch that ran the probe
admits the probe and nothing after it.

## What the probe did NOT test

Whether the decoder's key sequence is BETTER than Layer B's on any corpus — no measurement was
taken and none is implied by the finding; the chord-quality half of the legacy step, separately not
ported; and any other consumer of the legacy stabilization step.

## The incidental finding, kept apart and rowed at [[OI-353]]

Establishing which arm ships (step 1) met six comments in `src/` describing the production record
path as *default OFF* while the configuration sets its default to true. It is not an answer to this
row's question, so it is not part of the finding; it is rowed on its own.

## 2026-08-09 (CC, `cc_instruction_return_continuation_2.md` Task 0) — the owed correction is made, and this row's subject is discharged

**On the user's Ruling 15 of `cowork_rulings_2026_08_09_second_stop.md`**, which licenses exactly
the act the section above records as owed, and requires the non-equivalence to be carried visibly
rather than worded away.

**What was corrected, at the section that owns the rule** (`ARCHITECTURE.md`, Layer 6). The rule's
precondition half no longer names one implementation. It now requires that the per-region key
sequence the grouping runs over **has already been smoothed**, and states that **two designs meet
that requirement, one per arm**: on the production record arm, the joint decoder's global dynamic
program whose state carries the tonality and whose key transitions carry separate stay and change
branches, with the derived per-region fields supplied natively by the record; on the legacy arm,
that arm's own smoothing-and-stabilization step. The reason the wording had to change is stated
with it — the former text described an arm that does not ship, and a specification that misdescribes
the code cannot be the compliance standard (#10).

**What was preserved (#12).** The former heading wording — *"OVER STABILIZED REGIONS"* — and the
former **OPEN QUESTION** paragraph are both kept in place at the home, marked as former, so a reader
meets what the specification used to say and what answered it. The register entry's former recorded
defense — *"it leverages the key/mode fields and the stabilization Pass 4 already performed"* — is
preserved in that entry's own corrected defense field.

**What was re-taken.** **D-472**'s `verbatim`, its `title` and its recorded defense are re-taken
from the corrected home, so the register quotes the specification rather than a superseded reading
of it.

**The non-equivalence is stated at the home and stated as UNMEASURED.** Layer B erases a one-region
key island unconditionally; the decoder's key-transition term only makes one expensive, so an island
survives where the content evidence outweighs two key changes. **No corpus comparison of the two key
sequences has been taken**, none is implied by the correction, and nothing claims either sequence is
the better one (#24). What the difference does not do is leave the grouping un-preconditioned, for
the reason the section above already gives.

**What this act did NOT do.** No behaviour changed, no golden moved, no corpus of scores moved,
nothing in `tools/robust_stop/` moved, no fix to inference and no design. The incidental finding
stays where it was put, at [[OI-353]], which remains OPEN on its own subject.
